# Zeus 硬件与近存架构 {#hardware-model}

Zeus V3 将矩阵计算、向量计算、数据变换和数据搬运交给不同执行单元。矩阵右操作数可以驻留靠近计算逻辑的 LDG 3D DRAM，当前激活、结果和临时工作集则放在每核的 L2 Buffer 中。编写 Triton kernel 时，需要同时确定数学关系、数据位置、核间划分和临时结果的生存期。

本章先介绍双核系统及各核的存储和执行单元，再说明算力、吞吐、容量与带宽。图中的位置表示逻辑连接，不表示封装剖面或芯片尺寸。各项吞吐先按每拍给出，再注明换算所用的频率；实际部署的时钟、可用核和存储配置，以相应设备信息为准。

## 系统、计算核与任务

### Host 与 Device

Host 运行 Python 或 C/C++ 应用，检查参数，分配设备存储，组织 kernel 调用，并接收执行结果。Device 执行已编译的 Zeus 程序。框架中的一个算子可以包含数据转换、一次或多次 kernel 启动、同步和结果封装，因此算子调用耗时通常大于其中某一段设备计算的耗时。

宿主侧与设备侧可以各自推进工作。提交一个 kernel 后，宿主得到的是任务已提交这一事实；需要读取设备产生的结果时，还必须等待相应工作完成。Python 对象持有的输入、输出和 LDG 存储，应在设备最后一次访问结束前保持有效。对象不再被当前 Python 语句使用，并不等于设备已经结束读取。

### 计算核是工作与存储归属的基本单位

一个 Zeus 计算核包含控制、计算和搬运资源，以及与之对应的片上存储和 LDG 访问路径。多核执行时，不能把所有核的本地资源合成一块无差别的共享空间。每个核使用哪个 LDG 基址、读哪部分输入、写哪部分输出，都需要由运行时参数和 kernel 的划分方式共同确定。

贯穿案例采用两个核。核 0 和核 1 可以读取同一组 GDG 输入，但写入各自负责的输出区间。矩阵乘还需要为每个核准备相应 LDG 数据。两个核都计算一个权重矩阵的不同输出列时，可以分别保存各自需要的权重行；两个核都需要完整权重时，则涉及复制或其他明确的数据供给方式。核数增加不会自动建立权重分片。

这里的“核”也不同于设备编号。`zeus:0` 选择运行时管理的一个设备，而 `tl.program_id(0)` 在本书采用的启动方式下标识该次 kernel 内参与执行的核实例。切换设备与改变核内任务划分属于两个独立操作。

### 数据并行、单元并行与宿主并发

并行有不同的作用范围。核间数据并行让多个核处理互不重叠的输出；核内单元并行让搬运、矩阵计算、向量计算等在依赖允许时重叠；宿主与设备并发允许 CPU 在设备执行期间处理其他工作。三者的资源和同步方式不同。

以 $N=2500$、每 tile 1024 个元素的向量加法为例，两个核分别获得两个 tile 和一个 tile。核 0 处理 2048 个有效元素，核 1 处理 452 个有效元素。即使核 1 提前完成，整个任务仍要等待核 0。若在核 0 内重叠输入搬运与计算，可能缩短它的执行时间；单纯给核 1 分配更多空闲执行单元不能减少核 0 的工作。

| 层次 | 可以组织的工作 | 依赖或限制 |
|---|---|---|
| Host 与 Device | 参数准备、任务提交、设备计算 | 结果读取与存储生命周期 |
| 多个计算核 | 独立输出分区、分片矩阵 | 核数、数据归属、跨核合并 |
| 同核不同单元 | LD、PE、VP、DT、ST、LW | 数据就绪、缓冲区复用、发射资源 |

## GDG、L2 Buffer、LDG 与 WL1

### GDG：外部数据交换空间

GDG 用于保存普通输入输出、指令和运行参数，也是多个 kernel 之间交换普通张量的常见位置。CPU 准备的输入进入设备后，通常先形成 GDG 张量；计算核通过 LD 路径把要处理的区域装载到本核 L2 Buffer，结果再经 ST 路径写回 GDG。

GDG 中的二维张量仍需遵循 shape、stride 和有效容量。一个张量位于 GDG，并不说明它一定是连续的，也不说明任意相邻地址都可访问。框架切片、共享存储和原地更新可能使不同参数引用重叠的范围，宿主封装必须如实传递这些关系。

### L2 Buffer：每核 512 KiB 的片上工作存储

L2 Buffer 是采用 SRAM 实现的核内工作存储，每核物理容量为 512 KiB，即 524288 字节。输入 tile、激活、部分和与临时结果都使用这块空间。编译器及硬件资料中的 AL2、OL2 表示相关输入或输出用途，不是额外增加的两块 512 KiB 存储。L2 Buffer 也不采用 CPU 缓存的自动替换或按需缺页规则。

L2 Buffer 中的空间由编译器根据 tile、布局、数据类型和生存期分配。顶部 1 KiB 为运行时保留，栈、参数暂存和布局转换还可能占用其他区域；512 KiB 不能全部作为 tile 预算。一个 Triton 临时变量可能与其他变量复用存储，也可能在布局变换时产生另一份物化结果。因此，源码中的变量个数不能直接用来估算 L2 Buffer 分配。开发者首先控制 tile 与同时存活的数据，之后查看编译器给出的真实分配结果。

普通向量运算使用 L2 Buffer 中的数据；矩阵计算的激活也经 L2 Buffer 进入 PE 输入路径。PE 结果回到 L2 Buffer 后，可以继续做向量后处理、变换或写回。若中间结果能在核内完成所有消费，就有机会省去一次 GDG 写出和下一次读入。

### LDG：与计算相邻的 3D DRAM

LDG 是 Zeus 近存架构中的 3D DRAM 数据空间。PE 可以经专用矩阵读取路径从 LDG 读取操作数，不要求先把整个右操作数复制到 L2 Buffer。较大的、反复参与矩阵计算的数据可以驻留 LDG，而 L2 Buffer 主要承载当前激活 tile、结果和临时工作集。

LDG 中既可以保存推理期间不变的模型权重，也可以保存运行过程中写入、增长或重用的 KV Cache 和其他状态。代码中的 `memory_type="weight"` 是真实接口标识符，表示相应的存储与矩阵操作数访问方式；它没有把所指数据定义成只读常量。需要修改数据时，应选择与其物理布局匹配的写入路径，并建立写入与后续读取之间的顺序。

近存组织的直接意义，是让 PE 反复消费 LDG 中的矩阵块时，无需把这些块都经过 GDG 到 L2 Buffer 的普通输入路径。它仍然需要 LDG 内部读取、WL1 读取与分发、激活到达和输出保存。性能取决于这些环节的配合；只看到数据位于 LDG，不能据此断言所有数据等待都已消失。

### WL1：LDG 访问与矩阵数据分发

WL1 负责组织 LDG 访问和矩阵数据分发，管理相应读取、布局解释和向 PE 分发数据的过程，也提供外部读写访问接口。理解数据路径时，应把它与 LDG 的存储容量概念分开：LDG 回答数据存在哪里，WL1 回答这些数据怎样按矩阵计算所需顺序送到 PE。

在本书使用的 BF16 普通布局中，一个 $128\times64$ 的 miniblock 包含 8192 个元素，共 16 KiB；它按 8 路 WL1 组织，每路对应 2 KiB。这个比例是布局与访问组织的一部分。它不等于 kernel 直接控制 8 个独立线程，也不意味着程序中 `BLOCK=128` 就自动对应一个完整 miniblock。

LW 从 L2 Buffer 读取待写数据，按目标布局组织后，经 LDG 的写访问路径完成更新。完成信号应对应写入及响应均已结束，不能把“已发射 LW”当作“PE 已经可以看到新内容”。专用 K/V 布局的读写接口与实例见 [LDG 数据布局与访问](#ldg-memory)。

## 计算、变换与搬运单元

### CT：控制与发射

CT 执行控制流和相关标量操作，组织循环、分支、地址状态及指令发射。`tl.program_id(0)`、循环计数、当前 tile 的起点和描述符位置，最终都需要与控制及地址计算配合。它们虽然不像矩阵乘那样处理大量数值，却会影响短 kernel 和小 tile 的开销。

一个 Python 表达式不一定对应一条设备指令。建立块指针可能生成描述符设置；进入 K 循环可能更新位置与有效范围；类型转换可能加入计算或搬运。理解 CT 的作用有助于解释为什么把 tile 切得很小，有时会增加总时间：每块处理的数据减少了，控制和描述符工作却没有按同样比例减少。

### VP：向量、逐元素与归约

VP 承担适合向量路径的逐元素计算、激活和归约等工作。向量加法的两个 BF16 输入先被装载，按源码要求转换或参与计算，最后形成输出 tile。RMSNorm 还需要平方、归约、缩放以及可能的广播。

一个逻辑向量可以长于单次底层操作的处理粒度，编译器负责合法化与分配。源码中的 `tl.arange(0, BLOCK)` 表达一组逻辑索引，不是在申请同样数量的物理线程。把 `BLOCK` 从 1024 增到 2048，首先改变的是 tile 和工作集，不能直接解释成硬件线程翻倍。

每个计算核有 VP0–VP3 四条物理向量通道。一个 kernel 能否同时使用它们，取决于编译器生成的任务、输入是否就绪、L2 Buffer 访问是否冲突，以及输出之间是否存在依赖。四个 VP 的存在不意味着每条 `tl.sum` 都被拆为四份，也不意味着连续写出的四条表达式一定同时执行。多 VP 策略与片上布局的选择见[性能分析与优化](#performance)。

### PE：矩阵乘累加

PE 执行编译器映射到矩阵路径的运算。常用数学形式为

$$
C[M,N]=A[M,K]W[N,K]^T.
$$

其中 A 是激活侧矩阵，W 以 $[N,K]$ 形式描述 LDG 中的右操作数，对应数学矩阵 $B[K,N]$ 的转置。计算前要确定 W 的 pack 与描述符是否匹配；运算中要确定每个输出 tile 的 K 累加范围；计算后要确定累加精度、输出转换和后处理。

硬件资料中的矩阵维度名字与算法中的 M/N/K 不完全相同。算法 M 对应激活的空间方向，算法 K 对应收缩方向，算法 N 对应 LDG 操作数的输出通道方向。讨论 kernel 时始终先写出数学式和两侧 shape，再映射到硬件描述符，能避免把两个不同含义的 K 混在一起。

源码用普通 `tl.dot` 表达矩阵计算，由编译器根据类型、shape 与布局选择 PE 模式和 minitile。开发者应优先确定输入、输出、精度和物理数据契约；改变底层计算模式并不能修复 pack 错误或缺少部分和的问题。

### DT：片上数据变换

DT 处理片上数据搬运与维度变换，输入和输出通常位于 L2 Buffer。一个逻辑转置可能只是改变描述方式，也可能需要把数据重新排列为下一个单元可接受的物理形式。是否实际发生搬运，需要结合消费者和生成结果判断。

例如，矩阵运算希望按列消费一个普通行优先 tile 时，编译器可能需要转置或布局转换；LDG 操作数若已经采用目标物理布局，相关 `tl.trans` 则可能被吸收到 PE 描述符语义中。不能把所有 `tl.trans` 都累计成一次完整数据复制，也不能假定所有 reshape 都没有成本。

每核同样有 DT0–DT3 四条物理变换通道。DT 的工作量按移动的字节数、行列形状和访问模式理解，不计入 PE 的 MAC 或 VP 的浮点算力。多个 DT 可以服务不同的变换任务，但它们仍会竞争 L2 Buffer 的端口或 bank；把 DT 数量乘以单通道接口带宽，只能得到接口容量之和。

### LD、ST 与 LW

LD 把外部输入装载到 L2 Buffer；ST 把结果从 L2 Buffer 写出到目标外部空间；LW 将 L2 Buffer 中的逻辑矩阵写入 LDG，并可完成对应的物理排列。普通字节复制与带布局变换的写入服务于不同目的。

若 Host 已经生成正确的 LDG 字节布局，装载应保留该字节序。若设备刚计算出一个行优先状态矩阵，可以在合适条件下用 LW 转为所需布局。将已经 pack 的字节再次作为逻辑矩阵交给 LW，会再做一次变换；把未经 pack 的矩阵按原样拷入 LDG，再使用矩阵描述符读取，也会读取错误元素。

| 单元 | 输入与输出的主要关系 | 典型源码或工作 |
|---|---|---|
| CT | 参数、状态到控制与地址 | 循环、条件、分区、描述符更新 |
| VP | L2 Buffer 到 L2 Buffer | 逐元素运算、激活、归约 |
| PE | L2 Buffer 激活与 LDG 操作数到 L2 Buffer 结果 | `tl.dot` 与累加 |
| DT | L2 Buffer 到 L2 Buffer | 需要物化的数据变换 |
| LD/ST | GDG 等外部空间与 L2 Buffer 之间 | 普通张量 load/store |
| LW | L2 Buffer 到 LDG | 带布局变换的权重或状态写入 |

## Zeus V3 的容量、算力、吞吐与带宽 {#hardware-throughput}

### 频率、单核与双核口径

计算能力先按执行单元每拍可完成的工作计数，再乘其运行频率。PE、VP 使用系统计算时钟，DT 与控制侧使用 core 时钟；时钟管理单元可以选择和分频，两类时钟不必相同。本节 PE、VP、DT 和核侧搬运接口均按相应时钟为 400 MHz 换算。400 MHz 可由 2 GHz PLL 经五分频并正确选择、使能相应路径得到，并非上电即保证的默认运行状态。

完整双核配置包含两个同类计算核。双核列表示两个核同频时的结构容量之和；一个 kernel 仍需要足够且均衡的工作、正确的数据分片和持续的数据读取，才能接近这一容量。不要把单核的测量周期除以双核容量，也不要把 PE 拍与另一时钟域的 trace 拍直接等同。

### 存储容量与可用工作区 {#memory-capacity}

容量按存储的归属分别统计。完整双核 Zeus V3 配置包含两组 GDG，每组物理数据容量为 920 MiB；LDG 按核归属，每核物理数据容量为 14.375 GiB。下表统计数据位对应的容量，不包含额外的 ECC 校验位；MiB、GiB 分别表示 $2^{20}$、$2^{30}$ 字节。

| 存储 | 每组或每核物理数据容量 | 双核设备合计 | 应用预算还需扣除 |
|---|---|---|---|
| GDG | 每组 920 MiB，共两组 | 1840 MiB | 保留区、指令、参数及已有分配 |
| LDG | 每核 14.375 GiB | 28.75 GiB | 保留区、权重、KV、索引表及对齐开销 |
| L2 Buffer | 每核 512 KiB | 1 MiB | 顶部 1 KiB、栈及其他临时量 |

Table: 完整双核 Zeus V3 的物理数据容量与应用预算

GDG 与 LDG 的容量来自存储阵列组织：每个 bank 有 7360 行，每行 128 个 32 B 数据位置，即 28.75 MiB。每组 GDG 有 16 个有效 MC，每个 MC 连接两个 bank，得到 $16\times2\times28.75=920$ MiB。每核 LDG 的 256 个有效 MC 同样各连接两个 bank，得到 $256\times2\times28.75=14720$ MiB，即 14.375 GiB。冗余替换通道不作为额外应用容量累加。

::: {.caution}
表中是完整配置的物理数据容量，不是一次分配可以获得的空间。
实际可用量还取决于启用的 bank、保留与修复配置、运行时分配和对齐。
例如 GDG 每组虽使用 1 GiB 地址窗口，数据阵列容量为 920 MiB；地址窗口、仿真映射范围与可分配容量不能混用。
:::

双核合计拥有 1 MiB 的 L2 Buffer，但它由两个独立的 512 KiB 工作区组成，一个核不能借用另一核的空闲部分来放大自己的 tile。LDG 同样要按核核对；两核各保存一份相同权重，会产生两份实际占用。GDG 的多分组容量也不意味着一个连续分配可以跨越任意分组。

计算 L2 Buffer 工作集时，先统计同时存活的输入、累加器、输出及布局暂存，再考虑对齐和双缓冲。最终以编译器的分配结果判断是否容纳得下；只将张量的逻辑元素数乘以元素字节数，可能低估实际占用。仿真环境中的容量配置仅用于该环境，不能当作部署设备的物理规格。

### PE 的数据类型组合与 MAC 数

每核 PE 阵列包含 8 个 group，每 group 有 8 个 PE，每 PE 含 16 个 ALU，每 ALU 有 8 个 MAC cell。因此每核共有 $8\times8\times16\times8=8192$ 个 MAC cell。一个 cell 每拍处理的有效乘积数由激活与权重两侧的格式组合共同决定。

本节 FP8 指 E4M3FN；其他 FP8 编码不能直接套用这些能力。类型与编码见[量化矩阵乘与 UScale](#quantized-matmul)。以下按一次乘法和一次加法合计 2 ops/MAC 统计。BF16 和 FP8 纯浮点行使用 TFLOP/s，INT8 与混合格式行使用 TOPS；两类单位均表示每秒 $10^{12}$ 次所列操作。该计数不承诺任意浮点表达式具有单次舍入 FMA 语义。

| 激活 × 权重 | MAC/核/PE 拍 | 单核 400 MHz | 双核 400 MHz |
|---|---:|---:|---:|
| BF16 × BF16 | 8192 | 6.5536 TFLOP/s | 13.1072 TFLOP/s |
| INT8 × INT8 | 16384 | 13.1072 TOPS | 26.2144 TOPS |
| FP8 × FP8 | 16384 | 13.1072 TFLOP/s | 26.2144 TFLOP/s |
| FP8 × INT4 | 32768 | 26.2144 TOPS | 52.4288 TOPS |

Table: PE 按操作数组合计数的结构算力，MAC 按 2 ops 统计

表中的 INT4 行明确要求 FP8 激活与 INT4 权重，不表示 INT4×INT4 或 INT8×INT4 是相同的原生模式。类型转换、UScale、尾块、阵列填充以及累加反馈都会影响实际运行。编写 Triton 时仍用普通 `tl.dot` 表达数学运算，由编译器选择可用路径；不能把任意两个占位宽相近的数据类型当作可互换模式。

计算算力利用率时，分子应是需要完成的有效 MAC，分母为相同核数、模式、时钟及计时区间下的容量。例如 BF16 单核在 T 个 PE 拍内的容量为 $8192T$ MAC；补齐区和重复计算不能作为额外有效工作抬高利用率。

### VP 的输入宽度与逐元素算力

每个 VP 通道内部有 A、B 两组计算流水，每组各有 32 lane。宽模式让两组使用相同的运算配置，分别处理一批数据中的前 32 个和后 32 个元素，再合并两组结果。级联模式用于单操作数路径：同一批 32 个元素先经过 A，再把中间结果送入 B；两组可执行不同的前后级运算，最终仍产生 32 个元素的结果。

![单个 VP 的两组 32 lane：宽模式并行，级联模式接续处理同一批元素](assets/vp-pipelines.svg){width=100%}

图中以 BF16 单输入的逐元素路径为例，$f$、$g$ 表示相应模式支持的运算阶段，不表示任意两个 Triton 表达式都能合并成一条流水。箭头表示数据依赖，不表示整批数据在一个时钟拍内完成。一个核的四个 VP 是四个独立通道；每个通道内部都具有图中的两组结构，不能把两组当作两个可独立调度的 VP。

有效输入宽度还取决于数据类型。FP32 在两种模式下每拍最多形成 32 个有效元素，宽模式的后 32 lane 不承接另一批 FP32 输入。BF16、FP8 和 INT8 在相应宽模式下最多为 64 个；采用级联模式时则为 32 个。INT8 入口先转换为 FP32，再进入浮点运算组，不代表一组独立的 INT8 整数 ALU。具体路径由编译器根据运算及类型选择。

| 输入与模式 | 元素/通道/VP 拍 | 四通道合计/拍 | 单核 400 MHz |
|---|---:|---:|---:|
| FP32 | 32 | 128 | 51.2 G 元素/s |
| BF16，宽模式 | 64 | 256 | 102.4 G 元素/s |
| FP8，宽模式 | 64 | 256 | 102.4 G 元素/s |
| INT8 转 FP32，宽模式 | 64 | 256 | 102.4 G 元素/s |
| 上述窄格式，级联模式 | 32 | 128 | 51.2 G 元素/s |

Table: 输入连续有效时的 VP 入口与逐元素吞吐上界

若每个有效元素只做一次浮点加法或乘法，51.2 G 元素/s 对应 51.2 GFLOP/s，102.4 G 元素/s 对应 102.4 GFLOP/s。双核同频时的结构和为上述数字的两倍。这里计的是一次加或一次乘；不能因流水内部还包含其他阶段就直接再乘二，或据此承诺所有复合函数都达到同一结果率。

每个 VP 的 L2 Buffer 数据接口有 1024 bit 读口和 1024 bit 写口。两个完整输入向量需要分次读取时，读取带宽会约束表中算术吞吐；归约、级联函数、转换和输出重排也有各自的代价。普通 VP 向量路径不提供可由本表推导的 INT32 SIMD 算力，部分 i32 与浮点转换会走 CT 等路径。源码支持某个数据类型，不等于每种执行单元都为它提供同样的吞吐。

### DT 的字节吞吐

每个 DT 通道的读、写有效数据口均为 256 bit，每方向一次握手传输 32 B。按 400 MHz、每拍有效传输计算，单通道为 12.8 GB/s，单核四通道为 51.2 GB/s，双核八通道为 102.4 GB/s。

| 范围 | 每方向每拍容量 | 400 MHz 每方向容量 |
|---|---:|---:|
| 单个 DT | 32 B | 12.8 GB/s |
| 单核四个 DT | 128 B | 51.2 GB/s |
| 双核八个 DT | 256 B | 102.4 GB/s |

Table: DT 端口容量之和，实际变换还受访问模式和冲突约束

一次 B 字节的复制通常读 B 字节并写 B 字节；把两个方向相加不能把有效复制量改成 2B。非连续访问、短行、部分有效掩码和 L2 Buffer 冲突可能降低每拍有效载荷。DT 的搬运能力用字节计量。

### GDG 端口与核侧搬运带宽 {#gdg-bandwidth}

GDG 与核内 L2 Buffer 之间通过 LD/ST 搬运数据。每核读口和写口的有效数据宽度均为 1024 bit，即每个有效传输拍承载 128 B。按核侧接口 400 MHz 换算，每方向的端口带宽为 $128\times400\times10^6=51.2\times10^9$ B/s，即 51.2 GB/s。

| 数据路径 | 每核每拍有效数据 | 400 MHz 单方向端口带宽 |
|---|---:|---:|
| GDG → L2 Buffer，LD | 128 B | 51.2 GB/s |
| L2 Buffer → GDG，ST | 128 B | 51.2 GB/s |

Table: GDG 与 L2 Buffer 之间的核侧搬运带宽

51.2 GB/s 按连续有效传输计算，不是单个 kernel 的端到端实测带宽。一个读请求不能把读口和写口带宽相加；多个核访问 GDG 时，还需要考虑共同经过的互连与存储资源。

短请求、事务对齐、互连争用、存储响应和发射间隙都会影响有效载荷。Host 与 Device 间的传输还经过宿主互连，其速率不能由上述片内端口宽度推导。比较性能时应注明数据起点与终点、核数、频率，以及按有效字节还是读写总流量计数。

### LDG 的两条访问路径 {#ldg-bandwidth}

LDG 需要区分两条路径。矩阵读取由每核 8 路 WL1 向 PE 供数，服务于矩阵操作数；L2 Buffer 与 LDG 之间的原样 LD/ST 访问则搬运已有物理字节，走核侧搬运和 WA/WL1 接口。两者使用的并行度不同，带宽不能互换。

| 数据路径 | 每核计数口径 | 400 MHz 条件下的带宽 |
|---|---|---:|
| LDG → 8 路 WL1 → PE | 连续读请求，每 MC 15 个 credit、平均 23 拍周转 | 约 2.14 TB/s |
| L2 Buffer ↔ LDG，原样 LD/ST | 每方向 128 B/拍的接口 | 51.2 GB/s |

Table: Zeus V3 的 LDG 矩阵读取与原样字节访问

在矩阵读取路径上，每路 WL1 连接两个 hub，每个 hub 向 16 个存储控制器分发请求；两组 hub 均参与时，共有 $8\times2\times16=256$ 个 MC 通道。一次 MC 读取贡献 32 B，一个 16 KiB miniblock 对应每个 MC 各返回两次数据。

每个 MC 的读响应缓冲采用最多 15 笔在途请求的 credit 约束。若一次请求直到 credit 回收的平均周转为 23 拍，256 个 MC 的合计读取带宽估计为

$$
B_{\mathrm{credit}}=256\times32\times\frac{15}{23}
\approx5342.6\;\text{B/拍}.
$$

按 400 MHz 换算，$B_{\mathrm{credit}}\approx2.137$ TB/s，通常写作每核约 2.14 TB/s。在连续请求且每路 credit 保持有效利用时，每出数 16 KiB 对应的稳态平均间隔为 $16384/5342.6\approx3.067$ 拍。单次读请求则按从请求发出到数据就绪的时间单独计量。23 拍的周转估计包含跨时钟、MC 调度、存储读延迟、ECC 和数据返回。

GB/s、TB/s 使用十进制单位，KiB 使用二进制单位。当前 Zeus V3 的约 2.14 TB/s 是上述条件模型值；实际速率还受读写争用、行切换、ECC 配置、时钟比例、请求形状和 PE 消费节奏影响。只启用一个 hub 时，不能沿用 256 MC 的并行度。

### LD/ST、部分写与拷贝有效带宽

L2 Buffer 与 LDG 之间的原样 LD/ST 访问经 DMA、互连和 WA/WL1 接口，核侧与 WA 接口均以 128 B 为一个完整传输拍。一次完整读访问选择 4 个 MC，各返回 32 B；写访问按有效字节掩码向最多 4 个 MC 分发 32 B 子块。它没有展开为矩阵读取时的全部 256 个 MC，因此不能套用约 2.14 TB/s 的模型值。

128 B 接口在 400 MHz 下对应 51.2 GB/s 的单向端口容量。在就绪条件满足时可以连续接收请求，不能因为一次访问涉及多个 MC，就假定每 128 B 必须花两拍。实际传输还包含描述符、发射、互连等待和存储响应。

部分写可能触发 MC 粒度的读改写：完整 32 B 掩码直接写入，部分有效的掩码需读取旧值、合并后写回，全零掩码不发起写入。追加 token 的耗时因此不一定与有效字节数成正比。目标格式、位置与掩码应匹配写入路径，并保留未更新 token 的内容。

拷贝速率还取决于计数分子。若 N 字节以 51.2 GB/s 读入、再以同速率写出，且两段不能重叠，按有效数据 N 计为 $51.2/2=25.6$ GB/s，按总流量 $2N$ 计为 51.2 GB/s。这是串行传输的条件算例，不是 LDG 固定规格。报告需注明读写路径、字节口径与计时范围。
