# 调试与正确性验证 {#debugging}

一个算子从源码到结果，会经过参数检查、编译、装载、执行和输出比较。调试的第一步是确定失败发生在哪一步。编译成功说明程序通过了相应转换；输出比较通过说明该输入满足既定数值要求；这两种结果都不能替代另一种检查。本章沿用向量加法，建立可以扩展到归约、矩阵乘和融合算子的定位方法。

## 编译问题定位

### 保存可以独立复现的输入

复现包应能回答四个问题：编译了哪份源码，使用哪套工具，传入什么参数，期望得到什么结果。除了 kernel 文件，还应保存 `signature`、`constants`、启动 grid、动态形状、输入 dtype 和 stride。只保存一段报错截图，通常无法判断失败来自类型特化、边界条件还是工具链配套。

将编译日志、诊断产物和输入分开放在一次运行的独立目录。新实验使用新目录，避免同名文件被覆盖后误把旧二进制当成新结果。下列命令从随书目录执行，使用[编译与运行](#compile-and-run)中已配置的 PyTorch 后端和 SDK：

```bash
ZECC_JIT_LOG=1 \
ZECC_JIT_LOC=full \
ZECC_JIT_DUMP_DIR=build/debug-add \
python examples/vector_add.py --numel 2500 --run-device
```

`ZECC_JIT_LOC=full` 请求源码映射与入口 TTIR，诊断产物保存在指定目录的特化子目录中。位置映射能帮助把指令或 IR 对应到源码表达式，但一次源码表达式可能展开为多个操作，优化也可能合并表达式。应同时阅读前后的数据依赖，不能仅凭行号认定原因。切换 SDK 或编译器后使用新进程，并记录实际加载的组件版本。

### 找到首个不满足约束的阶段

按编译产物的先后顺序检查，可以把一个长错误日志缩小到一条契约。首先确认 Python 模块能够被导入、kernel 被正确选中；再检查 TTIR 中的类型、循环和地址；最后检查 ZeusHigh 的描述符与执行单元映射，以及 ZeusLow 的指令和同步。末尾的“编译失败”常常只是上游失败的汇总信息，最早出现的诊断才更接近根因。

| 首个异常位置 | 优先检查 | 可缩小问题的动作 |
|---|---|---|
| Python 导入或特化 | 导入路径、参数名、常量值 | 只导入模块并打印签名 |
| TTIR 或前端转换 | dtype、广播、指针语义 | 保留一个 tile 与一种操作 |
| Linalg 或 ZeusHigh | rank、stride、布局、访存范围 | 对照转换前后的类型与描述符 |
| ZeusLow 或资源分配 | 活跃缓冲、资源容量、指令约束 | 缩小 tile，单独关闭新增优化 |
| 装载或启动 | 二进制与运行时配套、参数 ABI | 对照[编译与运行](#compile-and-run)的参数记录 |

Table: 编译与启动问题的检查顺序

以 RMSNorm 为例，`BLOCK_HIDDEN` 小于实际 `hidden_size` 时，单遍整行实现没有覆盖完整归约域。即使代码可以编译，得到的也是局部平方和。正确修复是使单遍 tile 覆盖整行，或采用明确的列分块算法。调整容差无法修复漏算的数据。类似地，把连续矩阵的 stride 套到转置视图上，会使地址计算与张量含义分离；应修正接口检查或地址公式。

### 缩小用例时保留触发条件

最小复现的目标是去掉无关因素，同时保留使错误出现的条件。若问题只在尾块发生，把 `numel=2500` 改成 `2048` 可能会让错误消失，却没有解释错误。先将输入内容简化为可识别的序列，再缩小 shape；始终保留至少一个越过 tile 边界的维度。

向量加法可依次用全零、全一和带正负号的短周期序列检查。全零适合发现未写入输出，全一适合定位重复计算或遗漏，非对称序列适合发现错位和输入交换。随机数用于补充覆盖，并记录随机种子与生成方式。随机种子相同但输入分布、生成库或量化步骤不同，仍可能得到不同输入。

多核问题先比较单核和双核的同一组逻辑输入。单核通过、双核失败时，重点看工作分配、核私有地址、输出所有权和同步。不能通过让两个核重复写同一输出、依靠执行先后来“修复”错误。若缩小用例改变了编译器选择的实现路径，应把这一变化记录下来，继续保留原始复现。

## 地址、布局与写回问题

### 先在纸上展开一个元素的地址

当输出错位时，先选一个明确的逻辑坐标，把它从 Host 张量一直追到装载描述符。以连续 BF16 矩阵 `X[65,250]` 为例，元素 `X[4,3]` 的元素偏移为 `4*250+3=1003`，字节偏移为 2006。这里至少有三个独立条件：Host 的列数确实是 250；kernel 使用的行步长是 250；指针运算使用元素偏移，没有再次乘以 2。元素类型由指针类型决定，重复乘以元素字节数会让地址扩大一倍。

再看一个合法的转置视图。原张量 `A[3,5]` 的步长是 `(5,1)`，`A.T` 的逻辑形状是 `[5,3]`，步长是 `(1,5)`。转置仅交换了逻辑轴，数据并没有自动重新排列。若 kernel 根据 `[5,3]` 猜测步长为 `(3,1)`，它读取的仍是一段合法内存，结果却属于另一个矩阵。这类问题通常不会触发越界错误。修复方式是传递真实步长，或在 Host 明确执行 `contiguous()`，同时让接口说明和计时边界包含这次转换。

对块指针，分别检查以下信息，不要把它们合并成一句“shape 正确”。

| 字段 | 在 `X[65,250]` 中的含义 | 常见错误 |
|---|---|---|
| `shape` | 完整逻辑矩阵 `(65,250)` | 写成 tile 的 `(4,256)` |
| `strides` | 元素步长 `(250,1)` | 写成补齐宽度 `(256,1)` |
| `offsets` | 当前块的逻辑起点 | 同时在 base 和 offsets 中加一次偏移 |
| `block_shape` | 本次处理的 `(4,256)` | 误认为扩展了真实分配 |
| `boundary_check` | 保护行、列边界 | 只保护行尾，遗漏列尾 |

Table: 用完整矩阵和当前 tile 分别检查地址

`order` 描述块指针访问维度的次序，不会把一个错误的 stride 修正为正确布局；`boundary_check` 依据描述符中的真实 shape 工作，如果 shape 本身写大了，也不会知道 Host 分配得更小。

### 用可辨认的数据区分几类地址错误

随机输入适合检验整体精度，定位地址时则应让坐标具有可辨认的模式。先让同一行的值相同、不同的行取不同值，再让所有行共享一条随列变化的序列。前一组检查行选择，后一组检查列选择。分别执行两组，能区分行列交换、固定偏移和整块重复。

BF16 只能表示有限精度，不要把大整数线性编号直接写入 BF16 后期待每个元素仍唯一。例如可以使用 `row % 8 / 8` 和 `column % 64 / 128` 两组有限周期值；发生重复时，围绕可疑位置缩小窗口，并改变周期复核。对于只检查搬运的调试 kernel，也可以选择支持的 FP32 类型保留更多标记精度，但这不能代替最终 BF16 路径的验证。

输出问题可按“从未写入、错误位置写入、重复写入”继续区分。运行前将输出初始化为与期望结果明显不同的有限值；运行后检查哪些位置保持原值。发现整块没有更新，先查该块是否分配给某个核，再查循环是否执行；发现前面正确、后面重复，先查 `tl.advance` 的步进和起始块。输入全零而输出也预置为零，会掩盖未写入问题。

### 保护区必须位于逻辑输出之外

为了检查尾块写回，可分配“有效区 + 保护区”，将保护区填入固定模式。描述符的 shape 仍是有效输出的 shape，不能扩展到整块分配长度。执行后既比较有效区，也逐元素检查保护区。这样才能发现“结果前 N 项正确，但一次完整 tile store 覆盖了 N 后方”的错误。

例如向量输出有效长度 2500，后面额外分配 64 个 BF16 元素。第三个 tile 的起点为 2048，合法写入数量为 452；保护区从索引 2500 开始。如果保护区改变，重点检查输出描述符是否把长度写成了 3072，或 `tl.store` 是否缺少对应边界检查。输入的零填充只保护读取，不能自动保护输出。

行归约还要检查相邻行。`X[65,250]` 的逻辑行之间没有六个 padding 元素；每行 tile 内部出现的六个补零位置并不属于全局张量。在写回时把 256 当成全局行步长，会在所有行上累计产生错位，而不只影响最后一行。

### LDG 布局错误优先检查打包和描述符

LDG 权重和 KV 数据不是普通 GDG 连续数组。`memory_type="weight"` 选择了相应装载语义，kernel 的逻辑形状必须与 Host 打包时的矩阵形状一致。特别是池化存储：为请求读取一个有效前缀时，完整池的 shape 应保持不变，只调整读取位置和有效长度。把整个池的列数缩成当前请求长度，可能改变物理块之间的距离。

定位 Matmul 时，可以让 A 只有一个 K 位置非零。此时输出应对应 W 的那一列，能在很少的运算中检查 LDG 的 N/K 映射。随后移动非零位置，依次跨过 64、128 和 K tile 的边界。这些边界来自本书普通 BF16 weight 布局和示例分块；采用其他 dtype、patch 或专用 KV 格式时，应使用那条路径自己的边界。

定位 KV 更新时，先完成一次“写入一个 token、读回该 token 和相邻 token”，再接上 attention。只比较最后的 attention 输出，无法区分更新坐标错误、页表错误和 softmax 误差。具体的 K 行写入、V 列写入以及普通 weight 布局与专用缓存格式的区别，见[分页 KV Cache 与 Attention](#attention-cache)。

## 资源与执行依赖问题

### 区分 L2 Buffer 容量和寄存器压力

tile 过大可能在不同阶段失败。L2 Buffer 容量错误反映工作张量的物理布局及重叠生命周期；寄存器分配失败则可能来自大量活跃地址、描述符状态、标量临时值或展开后的控制流。把两者都称为“显存不足”，容易选错修复方法。这里的 L2 Buffer 是程序工作存储，不包括 PE 内部的 AL1、OL1 等缓冲。

需要查看分配细节时，可在新进程中启用 L2 Buffer 分配报告，观察每个缓冲的物理地址、大小和生命周期。下面的配置关闭本次进程的持久缓存复用，使编译阶段有机会输出报告；它不改变 RMSNorm 的数学定义。

```bash
ZEUSHIGH_L2_ALLOC_REPORT=1 \
ZECC_JIT_CACHE_DISABLE=1 ZECC_JIT_LOG=1 \
ZECC_JIT_DUMP_DIR=build/rmsnorm-l2 \
python examples/rmsnorm.py --rows 65 --width 250 --run-device
```

报告中的 `[l2-alloc]` 行含有 `addr`、`size`、`alloc`、`life`、`shape` 和 `place` 等字段。`life=[a,b)` 是编译器用于分配的操作顺序区间，不是硬件周期；`place=reuse` 表明复用了地址，也不表示两个操作能够同时使用这块内存。查看错误前仍然存活的输入、FP32 中间值、输出和下一轮预取，往往比只看源码变量个数更有效。

若增大 `BLOCK_HIDDEN` 后 L2 Buffer 超限，先减小每次处理的行数，再考虑列分块的两遍归约。如果双缓冲刚打开便失败，检查同时存活的两套输入以及累加器，不要先减少数据精度。若 L2 Buffer 占用并不高，寄存器压力却随动态索引或静态展开显著增加，尝试恢复规则块描述符、减少一次展开的独立地址，或把大物理写入拆成可描述的块级操作。

| 变化后出现的症状 | 首先检查 | 有针对性的调整 |
|---|---|---|
| tile 变大后 L2 Buffer 超限 | 输入、累加器和转换临时值 | 减少行块或输出块 |
| 开双缓冲后超限 | 两套输入与跨轮存活值 | 减少预取工作集 |
| 展开循环后寄存器失败 | 独立地址和标量活跃数 | 保留循环、简化地址 |
| 增加 lane 后编译回退 | 每 lane 私有状态与容量 | 减小并行宽度并检查报告 |

### 单次正确、重复执行错误

重复调用失败通常应检查状态，而不是立即检查浮点公式。首先确认原地输入是否已经被前一次调用修改；其次检查 scratch 是否在每次需要时初始化，页表和有效长度是否已经更新，以及异步执行完成前相关存储是否被复用或释放。

Fused Add RMSNorm 的第二次调用读取的 X 已经是归一化结果，R 已经是更新后的 residual。如果测试希望两次输出相同，就必须恢复两份原始输入。KV 更新则相反：缓存状态应跨调用保留，但新 token 的 slot 必须不同，后续读取的序列长度应包含新 token。把这两种状态策略混为一谈，会产生“第一次通过，后面逐步偏离”的现象。

对于 Graph replay，要区分张量内容变化和存储地址变化。页表、slot 和长度可以在稳定缓冲中更新；捕获完成后重新创建同形状张量，可能并没有改变图中记录的地址。若 eager 路径正确而 replay 错误，先对照参与捕获的对象生命周期和实际地址，再检查 kernel 的数学表达。

### 识别缓冲复用引起的依赖错误

流水中存在两条不同的边：数据搬入完成后，计算才能读取；计算或写回最后一次使用完成后，缓冲才能被下一轮覆盖。第一条遗漏通常表现为读到旧输入，第二条遗漏则可能表现为多轮以后才出现错误。只测一个 tile 无法覆盖第二类问题。

可以按 1、2、3、5 个 tile 递增测试：一个 tile 检查基础计算；两个 tile 引入换槽；三个 tile 首次复用原槽；奇数个 tile 检查最终排空。在保证输入相同的前提下，分别关闭双缓冲和 Parallel-Executor，以判断变化来自哪一种调度。正常 Triton 程序的依赖由编译器生成同步；用户应修正别名与数据流表达，不能通过任意删除等待来消除错误或缩短时间。

发生挂起时，从最后完成的生产者和下一条等待的消费者开始检查：消费者等待的是哪份数据、生产者是否在当前分支实际执行、空工作核是否跳过了某个必需的协作步骤。某个等待指令停留很久只是现象，真正原因可能在更早的输入读取或控制流上。将问题缩成仍包含同样分支与迭代关系的用例，比把所有循环都删掉更有帮助。

## 精度与边界测试

### 先定义参考计算

数值比较必须先固定输入量化、计算精度、转换位置和输出 dtype。对于本书的向量加法，输入已经是 BF16，计算时转换到 FP32，再把结果转换为 BF16。CPU 参考应从同一份 BF16 输入开始，不能拿尚未量化的原始 FP32 数据代替输入。

```python
x32 = x_bf16.float()
z32 = z_bf16.float()
reference = (x32 + alpha * z32).to(torch.bfloat16)
```

当前配套实现的普通 BF16 下转换采用最近偶数舍入。位截断、最近偶数舍入以及每一步都转回 BF16，会产生不同结果。参考程序必须跟随算子契约中的转换位置，并显式使用与输出相同的 dtype。

一个可手算的检查点是 $1+2^{-8}$。在 1 附近，相邻 BF16 数的间距是 $2^{-7}$，该值位于 1 与 $1+2^{-7}$ 正中间；最近偶数舍入得到 1。再检查 $(1+2^{-7})+2^{-8}$，最近偶数舍入得到 $1+2^{-6}$。两个测试分别覆盖低位为偶数和奇数的中点，能区分最近偶数舍入与始终向下截断。它们只用于检查这个正常数范围内的转换规则，不代表已覆盖溢出或非有限值。

![BF16 最近偶数舍入在两个相邻中点上的不同方向](assets/bf16-rounding.svg){width=100%}

归约还受加法顺序影响。FP32 累加减小了误差，但并不保证不同归约树按位相同。矩阵乘应记录 K 维分块及累加 dtype，融合算子应记录中间 residual 的转换位置。对有限正常输入的误差要求与 NaN、Inf、次正规数、溢出和带符号零的行为分别验证，避免用一个全局误差阈值混合两类问题。

### 同时查看误差大小和位置

设参考输出为 $r_i$，设备输出为 $y_i$。最大绝对误差直接反映最坏元素差异，均方根误差反映整体误差规模。

$$
E_{\mathrm{abs}}=\max_i |y_i-r_i|,
\qquad
E_{\mathrm{rms}}=\sqrt{\frac{1}{n}\sum_i(y_i-r_i)^2}.
$$

逐元素判断通常采用 $|y_i-r_i|\leq a+r|r_i|$，其中 $a$ 为绝对容差，$r$ 为相对容差。参考值接近零时，绝对容差起主要作用。纯相对误差中的分母应明确写为 $\max(|r_i|,\delta)$，并记录 $\delta$；不同分母产生的百分比不能直接比较。

```python
actual = actual.float()
reference = reference.float()
error = (actual - reference).abs()
limit = atol + rtol * reference.abs()
failed = error > limit
max_abs = error.max().item()
rms = error.square().mean().sqrt().item()
failed_count = failed.sum().item()
```

这段代码用于有限值。开始统计前，先比较两边的 NaN 位置、Inf 位置与符号；有非有限值时，分别报告这些异常，再对有限位置计算误差。空张量也应在进入 `max()` 前单独处理。容差由算子的误差预算确定，在性能对比前冻结，不能为让某个优化版本通过而临时放宽。

如果差异集中在 `1024`、`2048` 等边界附近，应先查 tile 偏移与尾部写回；如果隔固定 stride 出现差异，应先查地址公式；如果每行末尾异常，应先查列 padding；如果整体随 K 增大而偏离，再检查累加精度和舍入。误差分布提供的是定位线索，最终仍需通过输入、IR 或逐步参考计算验证。

### 把复杂表达式拆成可比较的中间量

RMSNorm 可以依次比较平方和、逆均方根、缩放前输出和最终 BF16 输出。如果平方和已经错了，先查归约轴、完整归约域和 padding；平方和正确而逆均方根错了，再检查分母、epsilon 和近似函数；只有最终 BF16 不同，则回到转换边界。临时输出中间量会增加存储和改变调度，它用于定位数值来源，修复后仍需在原始完整 kernel 上复测。

Matmul 的类似方法是分别比较每个 K 块的部分积，以及逐块累加后的结果。第一块就错误，通常与输入布局、转置或类型有关；前几块正确、某一块开始错位，检查 K 偏移；全部单块正确但累加后不同，检查累加器是否保持 FP32、清零位置和加法顺序。对融合算子则先单独检查可见 residual，再检查以该 residual 为输入的归一化。

Attention 应保留三种参考。第一种直接计算完整 FP32 softmax 和乘积，用于检查数学目标；第二种按相同序列分块执行在线 softmax，用于定位递推；第三种增加设备路径上的概率 BF16 转换和部分输出转换，用于解释实现误差。不能只保留第三种而失去数学基准，也不能拿第一种按位要求替代实际实现的精度契约。

### 按接口契约设计边界集合

每个公开封装应明确哪些输入接受、哪些输入拒绝。连续向量示例不会自动支持任意非连续视图；不允许原地覆盖的接口应在调用前拒绝别名。对拒绝项的测试同样有价值，它验证用户不会因一个看似合法的调用得到静默错误。

| 类别 | 向量加法代表输入 | 需要验证的行为 |
|---|---|---|
| 空输入 | `numel=0` | 宿主直接返回，不启动无工作 kernel |
| 单个小块 | `numel=1, 888` | 边界读取、尾部写回、空闲核 |
| 整块 | `numel=1024, 2048` | 块边界、核分工、完整输出 |
| 尾块 | `numel=1025, 2500` | 末块不越界、不漏写 |
| 多块 | `numel=8193` | 循环步进与跨多轮缓冲复用 |
| 接口约束 | stride 或 dtype 不符 | 明确拒绝或走已定义的转换路径 |

Table: 向量加法的基础边界集合

归约和 Matmul 要分别覆盖每个相关维度。RMSNorm 至少区分行方向尾块与列方向 padding；Matmul 至少区分 M 尾块、N 尾块、K 尾块及多个 K 块。多核切 N 的特定实现若要求 N 可被核数整除，测试既要包含合法形状，也要验证非法形状被拒绝，不能把 `N // CORE_NUM` 当成通用尾部处理。

原地更新需要额外检查旧值的最后一次读取。Fused Add RMSNorm 会更新 residual，并写出归一化结果；输入 X 与 residual 必须按接口要求使用独立存储。测试除了最终输出，还要比较 residual，并确认输入中未参与计算的区域没有被覆盖。对于需要重复测量的原地算子，每轮测量前应恢复相同输入，恢复操作放在计时区间之外。

## 重放失败与验证修复

::: {.keep}
修复后先使用原输入、原常量和相同 PyTorch 参考重放失败。随书向量示例的 `--run-device` 通过 Triton JIT 启动 kernel，取回输出后调用 `torch.testing.assert_close`；不带该参数只运行 CPU 参考。下面先检查主线长度，再检查相邻块边界：

```bash
python examples/vector_add.py --numel 2500 --run-device
python examples/vector_add.py --numel 1025 --run-device
```
:::

保留源码、启动参数、输入、参考函数和诊断输出，使修复前后能重放同一用例。随机输入还需固定种子，或直接保存失败张量。确认原失败已修复后，增加相邻边界，最后重跑既有代表形状。例如修复第 3 个 tile 换槽错误后，仍要检查第 4、5 个 tile 和奇数尾块，避免只修正某个固定轮次。

JIT 是提交和编译入口，实际执行后端由 SDK 配置决定。功能模拟中的结果比较不能替代物理设备验证，也不能用来报告设备耗时；框架接入还要覆盖生命周期和上下游张量。提交问题时注明实际运行后端、SDK 版本、失败输入及误差位置。随书已完成的检查范围见[验证结果的阅读方式](#versions-and-examples)。
