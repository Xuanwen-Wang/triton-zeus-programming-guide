# 概述 {#overview}

Triton Zeus 用 Python 描述张量计算，由编译器把访存、计算和控制流映射到 Zeus V3 的执行单元。开发者主要决定每个程序实例处理哪些元素、怎样组织 tile、采用什么精度以及何时保存结果。编译器据此建立数据布局、分配片上存储、安排执行单元并生成依赖同步，最终输出可由 Zeus 运行时加载的二进制程序。

本书面向算子开发者、框架集成工程师和性能分析工程师。通过一个 BF16 向量加法，读者可以完成环境检查、编写 kernel、检查尾块、编译与执行，并理解相同程序为何会因任务分配和数据搬运方式而呈现不同性能。随后学习 LDG 3D DRAM 近存架构、矩阵布局与可变状态，再用归约、RMSNorm、矩阵乘、注意力和融合算子说明更复杂的计算组织。

## 适用范围与阅读路线

### 编程对象与边界

本书以 Zeus V3 单设备上的 Triton 算子为对象。一个算子通常由宿主封装和设备 kernel 两部分组成。宿主封装检查输入、分配输出、选择特化参数、启动 kernel，并向上层提供稳定的调用接口；设备 kernel 描述该次计算中的索引、数据流和数值运算。两者共同构成可使用、可测试的算子。

“单设备”允许使用设备内的多个计算核，也允许核内不同执行单元并行。跨设备通信、多机调度、整模型分布式策略和驱动部署管理超出本书的主要范围。阅读本书不要求掌握全部 MLIR 方言或指令编码；需要定位编译问题时，可以按[编译、执行与框架接入](#compile-and-run)介绍的方法查看对应阶段的产物。

本书使用 Zeus V3 的配套语言与运行时接口。形状、tile、核数和页面大小在每个示例中明确给出；它们首先服务于正确理解和复现，实际应用可在保持数学及布局契约的前提下调整。接口版本和示例验证范围集中列于附录。

### 按任务选择入口

首次接触 Triton Zeus 的读者，建议先完成[快速上手](#quick-start)中的向量加法，再阅读硬件与近存架构、编程模型。能在纸上解释每个输出元素由谁写出、最后一个 tile 如何处理以后，再开始修改 tile 和并行参数。这能使性能调优建立在清楚的输出归属上。

已有 GPU Triton 经验的读者，可以先阅读[从 GPU Triton 迁移](#migration)，重点核对程序实例与计算核的映射、设备内存的使用方式，以及 GPU 专属调优参数的适用性。Triton 源码看起来相似，并不意味着启动网格、缓存选项或硬件并行关系可以直接沿用。

框架集成工程师可从[编译、执行与框架接入](#compile-and-run)开始，理解 JIT、AOT、特化键和参数 ABI，再按[调试与正确性验证](#debugging)建立调用层回归。负责性能的读者应先明确计时范围，再使用[性能分析与调优](#performance)的方法对照输入、二进制和 trace。

### 三个需要同时建立的模型

数学模型说明要计算什么。例如向量加法逐元素独立，RMSNorm 先做行内归约，矩阵乘沿 K 累加，注意力则涉及历史状态与有效长度。它决定哪些操作可交换、哪些状态必须保留、误差怎样比较。

存储模型说明同一个逻辑元素在哪里。普通 GDG 张量用 shape 和 stride 描述；L2 Buffer 中的 tile 还要考虑物理行对齐和生存期；LDG 矩阵需要 pack、每核地址与相应描述符。数学上相等的两个矩阵，可能具有完全不同的物理字节序。

执行模型说明由谁处理、何时可读或可覆盖。核间分区决定输出归属，核内 CT、PE、VP、DT 和搬运单元依赖决定执行顺序。把三个模型结合起来，才能解释“结果正确但速度慢”与“地址合法但元素错位”这两类常见问题。

### 全书的贯穿案例

贯穿案例计算两个连续一维 BF16 张量的逐元素加法

$$
y_i = \operatorname{BF16}\bigl(\operatorname{FP32}(x_i)
    + \alpha\operatorname{FP32}(z_i)\bigr),
\qquad 0 \le i < N.
$$

上手阶段固定 $\alpha=1$。输入先按 BF16 存储，运算提升到 FP32，最后转换成 BF16。本文所称“FP32 参考计算”始终从已经量化为 BF16 的输入开始，因而包含了真实输入格式的影响。

第一组输入取 $N=2048$，每个 tile 包含 1024 个元素，恰好得到两个完整 tile。第二组取 $N=2500$，形成两个完整 tile 和一个含 452 个有效元素的尾块。两组输入共用一份 kernel 和数值定义，可以观察边界保护、核间分工以及任务量不均衡对执行的影响。

示例文件中的宿主函数拒绝非连续张量和不匹配的输入形状，分配独立输出。这样的契约使上手过程清晰，也为后续扩展 stride、广播或原地更新提供确定的比较基线。增加一种能力时，需要同时修改索引、宿主检查和对应测试，不能只删除一条检查。

贯穿案例之后，LDG 章节从 BF16 矩阵 B[K=128,N=256] 出发，将存储视图 W[N=256,K=128] 划为四个 16 KiB miniblock，演示 64 KiB 的物理排列；再以页长 1024、头维度 128 演示 K/V 各 256 KiB 的缓存页。这些例子说明为什么逻辑矩阵需要 pack、同一 token 的 K/V 写入位置为何不同，以及读写参数的地址类型为何不能互换。

## 一个算子由什么组成

### 宿主接口与设备 kernel

设备 kernel 的签名一般包含数据指针、运行时标量和编译常量。kernel 描述一个核实例的任务划分、装载、计算与保存；它通常不负责解释框架中的对象关系，也不负责判断两个 Tensor 是否来自同一个请求。

宿主接口把这些条件变成可使用的算子：确认 dtype 和设备一致，检查有效尺寸与所需布局，分配输出或工作区，选择经过支持的特化，启动任务并维护资源生命周期。对于 LDG，还要准备正确的 pack 与每核地址对象。设备代码和宿主接口共同构成算子，单独一个能编译的 JIT 函数还不包含完整调用契约。

### 编译期选择与运行时数据

编译期常量决定生成什么程序，运行时参数决定该程序处理哪份数据。向量加法中 `BLOCK` 和 `CORE_NUM` 是前者，`numel`、`alpha` 和三个数据地址是后者。同样的编译产物可以处理不同合法长度，但新的 dtype、tile 或布局选择可能需要另一份产物。

状态内容与特化也应分开。KV Cache 追加后，数据和有效长度改变，并不意味着每个 token 都必须重新编译 kernel；改变页面格式、某个静态维度或核分区，则可能改变编译契约。明确这种分工，可以避免无谓的编译开销，也能避免让旧二进制解释新布局。

### 参考结果与可观察输出

参考结果必须从 kernel 实际接收的输入格式出发。输入先转换成 BF16 时，参考应使用转换后数值；不能让参考读取原始 FP32，而设备读取已量化的 BF16。归约和矩阵乘还要指定累加与输出转换节点，KV 更新则要检查被写位置和未写区域。

一个可复现示例应具备明确输入、可执行入口、预期输出、误差标准和失败时保留的数据。后续章节延续这一写法。读者可以先复制完整示例，再按章节中的推导修改；正文短片段用于解释关键关系，不省略完整示例中的宿主检查。

## 软件栈与版本配套

### 从 Python 到设备执行

Triton Python 前端解析带 `@triton.jit` 装饰的函数，生成 Triton IR。Zeus 编译器继续处理结构化计算与内存访问，将其映射到 ZeusHigh 和 ZeusLow 表示，再生成 `.zbin`。ZECC 提供命令行编译入口，也通过 JIT 缓存库为运行时适配器提供编译能力。

运行时负责识别输入张量所在设备、组织调用参数、加载二进制并提交执行。PyTorch 接入由 `torch_zeus` 完成；安装相配套的 Zeus Triton 与运行时后，Triton kernel 的 Python 调用会进入 Zeus 适配路径。离线编译则可以在不启动设备 kernel 的情况下产出 `.zbin` 或用于链接的对象文件。

| 组件 | 算子开发者主要接触的内容 | 典型产物或行为 |
|---|---|---|
| Triton Python | kernel、类型、constexpr、grid | TTIR 与特化信息 |
| Zeus 编译器 | tile、布局、执行单元与同步 | Zeus IR、汇编、`.zbin` |
| ZECC | 离线编译、JIT 编译接口 | `.zbin`、对象文件、编译元数据 |
| 设备运行时 | 分配、参数、加载、提交与同步 | 一次设备任务执行 |
| `torch_zeus` | Tensor 与 PyTorch 设备接口 | `zeus` 张量及框架算子入口 |
| 验证与分析工具 | 功能比较、时序与 trace | 误差、周期、执行轨迹 |

Table: 编程接口与软件栈的分工

### 配套安装的含义

可导入 `triton` 只证明 Python 找到了一个同名模块。Zeus 语言扩展、Python 启动适配器、ZECC、编译器、运行时以及 native 库需要组成同一套受支持的环境。上游 Triton、旧版本 Zeus wheel 或其他 checkout 的 Python 路径都可能与当前工具发生混用。

因此，安装采用所用 SDK 的配套包清单和安装说明。检查时同时记录软件版本与实际加载路径。源码环境还应记录编译器和 Triton 的提交标识，以及 build 目录对应的源码。更换工具链后，应重启需要使用新工具链的 Python 进程；旧进程可能仍持有已经加载的模块、native 库或内存缓存。

| 配套项 | 应记录的信息 | 作用 |
|---|---|---|
| 目标设备 | 型号、硬件版本、运行模式 | 确认目标与执行环境 |
| Python 与 PyTorch | 版本、解释器、模块路径 | 核对 Python 和 native ABI |
| Zeus Triton | 版本、构建标识、模块路径 | 核对语言与启动适配 |
| Zeus 编译器与 ZECC | 版本、可执行文件路径 | 核对代码生成与编译选项 |
| 运行时与 `torch_zeus` | SDK 版本、native 库版本 | 核对设备调用与参数契约 |
| 示例与验证环境 | 示例版本、输入参数、执行类型 | 保证结果可复现 |

### 正确性、时序与实际性能

不同验证环境回答不同问题。CPU 参考用于建立数值结果；编译检查验证源程序能否降级为目标产物；功能仿真比较设备程序的运算行为；CycleSim 与 VCS/RTL 提供各自模型中的时序证据；真实设备测试反映实际运行环境下的输出和耗时。对外报告时，必须保留执行环境这一项。

同一套 Python 设备接口可能连接到不同运行后端。`torch.zeus.is_available()` 成功表示运行时认为设备可用，本身不足以证明执行发生在物理芯片上。本文的 `--run-device` 表示进入已安装的 Zeus 运行时，执行地点由该环境的配置决定。确认执行后端的方法与结果记录方式见[调试与正确性验证](#debugging)。
