# Triton Zeus 编程模型 {#programming-model}

Triton kernel 描述一个程序实例如何处理一组张量元素。Zeus 后端把这样的程序映射到设备计算核，并在核内安排具体计算与搬运。理解这两层关系，可以避免把逻辑 tile 当作物理线程，或把源码中的并列表达式直接当作同时执行的指令。

本章沿用 $N=2500$、`BLOCK=1024`、`CORE_NUM=2` 的向量加法，逐步推导实例编号、全局索引、尾块和输出归属。随后扩展到二维 stride、归约与矩阵累加，为接口查阅和性能调优建立统一语言。

## Kernel 启动与程序实例 {#kernel-launch}

### JIT 函数与两类参数

`@triton.jit` 将一个 Python 函数定义为可编译的 Triton kernel。函数体中的 `tl.load`、`tl.store`、张量运算和控制流描述设备计算；宿主 Python 负责提供实际 Tensor、运行时标量、启动 grid 和特化参数。

```python
@triton.jit
def add_bf16(
    out_ptr, in1_ptr, in2_ptr, numel, alpha,
    BLOCK: tl.constexpr, CORE_NUM: tl.constexpr,
):
    core_id = tl.program_id(0)
```

`numel` 与 `alpha` 是运行时标量。相同的 kernel 特化可以接收不同合法值，而不要求它们全部变成编译常量。`BLOCK` 与 `CORE_NUM` 标为 `tl.constexpr`，编译时已知，影响 tile 形状、任务划分和生成代码。修改 constexpr 可能生成新的二进制或缓存条目。

是否采用运行时值取决于运算需要。tile 的静态尺寸往往适合作为 constexpr；输入有效长度适合作为运行时参数；某个数值如被用于编译期结构选择，则需要形成相应特化。把所有形状都改为 constexpr 会增加特化数量，把所有参数都改成运行时也可能超出可表达的静态 shape 条件。

### 张量程序与 Python 程序的区别

宿主 Python 负责调用函数、创建对象和管理设备；JIT 函数中的 Python 语法则用于构造设备程序。`tl.load` 得到的是设备张量表达式，`tl.arange` 产生逻辑索引集合，`tl.dot` 描述矩阵计算。它们不会在宿主按一个个 Python 元素解释执行。

因此，不能在 kernel 内随意调用任意 Python 库来处理设备数据。需要宿主确定的形状检查、文件读取和资源分配，应放在启动之前；需要设备根据输入值执行的分支和循环，必须使用当前 Triton 前端可表示的控制流。将 Python 变量名写成 `tensor` 并不决定其运行位置，参数类型和表达式语义才决定生成什么程序。

kernel 中的局部值也不能简单称为“寄存器数组”。编译器可能将它保留为标量状态、映射到核内 L2 Buffer、折叠到描述符，或在不需要物化时消除。源码应先表达逻辑数据关系，再通过编译产物确认物理位置。

### Grid 与核映射

Grid 描述一次启动的程序实例。标准 Triton 的 `tl.program_id(axis)` 返回逻辑实例在该轴上的编号，不能据此推断它落在哪个 GPU 物理计算单元。官方向量加法教程采用“一个 program 处理一个 tile”：宿主按 $T=\lceil N/B\rceil$ 启动 T 个实例，程序用 `program_id(0)*B` 得到起点。GPU 后端将这些实例映射为线程块等执行实体，由设备调度它们完成工作；逻辑实例数可以大于物理计算单元数。[Triton program_id](https://triton-lang.org/main/python-api/generated/triton.language.program_id.html)、[官方向量加法教程](https://triton-lang.org/main/getting-started/tutorials/01-vector-add.html)

本书使用的 Zeus 启动路径采用按核执行的方式。一维 `grid[0]` 进入启动适配器的核数配置；编译产物为参与核建立入口，在入口中给第 0 维 program ID 赋值。常规双核示例中，两个核实例分别取得 0 和 1。实例进入 kernel 后，依据源码中的分配公式和 `for` 循环完成各自的多个 tile。

::: {.caution}
Zeus 的 `grid[0]` 表示参与核数。逻辑 tile 多于核数时，必须在 kernel 内显式循环；当前启动路径不会自动把大型 grid 分批调度到这些核上。启动 grid、`CORE_NUM` 与二进制的核数配置必须一致。
:::

程序实例的编号与物理核位置也要区分。向量加法不使用核私有 LDG 分配，运行时按编号对应核位置；使用 LocalMem 对象时，运行时还会依据该对象所属的核安排实例。

::: {.note}
单核程序的 `program_id(0)=0` 表示第一个逻辑实例，不保证它始终位于物理核 0。使用 LDG 时，实例映射还必须匹配 LocalMem 的核归属和分片方式。
:::

以 $N=2500$、$B=1024$ 为例，需要完成三个 tile。若采用官方向量加法式的 GPU 写法，逻辑 grid 是 `(3,)`，实例 0、1、2 分别处理一个 tile。本书的 Zeus 示例使用 `(2,)`，由核 0 的循环处理 tile 0、1，核 1 处理 tile 2。若只保留 `offset=program_id(0)*BLOCK` 而删除核内循环，两个核只会覆盖前两个 tile；把 grid 改成 `(3,)` 也不能获得第三个可用核或自动补齐第三个 tile。

| 组织方式 | Grid 的取值 | 每个实例承担的工作 | Tile 推进由谁表达 |
|---|---|---|---|
| GPU 上每 tile 一个 program | 逻辑 tile 总数 | 通常一个输出 tile | 不同 program ID 与设备调度 |
| GPU persistent kernel | 按可驻留执行资源限制实例数 | 一个实例循环处理多个 tile | kernel 自行分配与循环 |
| 本书 Zeus 按核执行 | 参与核数（例：2） | 每核循环处理所属 tile | kernel 自行分配与循环 |

Table: 逻辑工作量与启动实例数的三种组织方式

Persistent kernel 指让较少的程序实例在一次启动内持续处理多份工作。Triton 官方 persistent matmul 示例限制启动实例数，并在实例内部按固定跨度推进 tile；这与 Zeus 示例的“少量实例加核内循环”在组织方式上相似，但不表示两种后端具有相同的物理映射、驻留保证或调度接口。“Persistent”也不表示程序跨多次 launch 常驻运行。[官方 Persistent Matmul 教程](https://triton-lang.org/main/getting-started/tutorials/09-persistent-matmul.html)

Grid-stride 描述循环的推进方式：编号为 c 的工作实例处理 $c,c+C,c+2C,\ldots$，跨度 C 等于参与实例数。在本书中可以按 tile 使用这种交错分配；上手示例采用的商余数法则分配连续区间，不能把所有核内循环都称为 grid-stride。两者都必须由源码明确给出遍历范围。[NVIDIA 对 grid-stride loop 的说明](https://developer.nvidia.com/blog/cuda-pro-tip-write-flexible-kernels-grid-stride-loops/)

实际编写 Zeus kernel 时，保持 grid 的核数、`CORE_NUM` 和二进制的核数描述一致。本书显式传入 `CORE_NUM`，不依赖适配器对同名常量的补全；二维与三维工作量先线性化，再由核内循环恢复坐标。前端能够接受多维 grid 语法，并不表示它已经建立 GPU 式的多维 program 调度。一个 tile 的元素数也不等于参与核数或核内执行单元数。

### 商和余数分配

设元素数为 $N$，tile 大小为 $B$，参与核数为 $C$。tile 总数、基础任务数和余数为

$$
T=\left\lceil\frac{N}{B}\right\rceil,\qquad
q=\left\lfloor\frac{T}{C}\right\rfloor,\qquad
r=T\bmod C.
$$

编号为 $c$ 的核从 $s_c=cq+\min(c,r)$ 开始，处理 $q$ 个 tile；若 $c<r$，再额外处理一个。这样任意两个核分到的 tile 数相差不超过 1，且它们的 tile 区间彼此相接。

对贯穿案例，$T=3$、$q=1$、$r=1$。两个核的分工如下

| 核编号 | 起始 tile | tile 数 | 有效元素区间 | 有效元素数 |
|---|---:|---:|---|---:|
| 0 | 0 | 2 | $[0,2048)$ | 2048 |
| 1 | 2 | 1 | $[2048,2500)$ | 452 |

Table: 2500 个元素在两个核上的任务分配

![贯穿案例中的程序实例、tile 和尾块映射](assets/tile-mapping.svg){width=100%}

这种方式平衡的是 tile 个数。尾块很小时，有效元素数和执行时间仍可能不均衡。它适合作为正确性清楚的基线，再按实际性能改进；不能只凭“tile 数相差不超过 1”断言负载已经均衡。

分配公式还可以证明覆盖性。第 $c$ 个核的结束位置是 $s_c+q+[c<r]$，恰好等于下一核的开始位置；第一个核从 0 开始，最后一个核结束在 T。因而各核 tile 区间首尾相接，既不重叠也不遗漏。这个证明与 tile 内的元素边界检查是两件事，二者都成立才保证完整输出。

### 小任务与空核

当 $N=888$、$B=1024$、$C=2$ 时，只有一个 tile。核 0 处理它，核 1 的循环次数为零。空核不应执行无效 load 或 store，也不应被要求产生其他核必须等待的数据。

当 $N=0$ 时，宿主封装直接返回空输出。对于更复杂的 kernel，空任务与空核还可能影响归约初始值、同步次数和输出初始化。不能用强行把长度夹到 1 的方式处理空任务，否则会产生原本不应发生的访问。

### 另一种分配：按 tile 的 grid-stride 循环

对独立 tile，还可以让核 c 处理 $c,c+C,c+2C,\ldots$。这是一种以 tile 为粒度的 grid-stride 循环：跨度为参与核数，而非 tile 的元素数。它将相邻 tile 交给不同核，适合用来比较连续区间分配与交错分配对工作量和局部性的影响。对应循环关系为

```python
for tile_id in range(core_id, total_tiles, CORE_NUM):
    element_start = tile_id * BLOCK
```

对三个 tile 和两个核，交错分配使核 0 处理 tile 0、2，核 1 处理 tile 1；前面的连续分配则是核 0 处理 tile 0、1，核 1 处理 tile 2。两者覆盖相同的任务集合，但输出归属和访问顺序不同。

这只是另一种任务划分，不能在其他部分不变时保证更快。对 LDG 分片矩阵，交错处理还要求当前核能访问对应权重；对需要连续批次复用的算法，它可能改变数据复用。选择分配方式之前先列出每个 tile 的输入、输出和状态归属。

## Tile、形状、步长与边界

### 逻辑索引与地址

一个 tile 内第 $j$ 个位置的全局索引为 $i=bB+j$，其中 $b$ 为 tile 编号，$0\le j<B$。只有 $i<N$ 的位置属于有效输入和输出。对连续 BF16 向量，元素 $i$ 的字节地址为 `base + 2*i`。

对最后一个 tile $b=2$，起点为 2048。位置 $j=0$ 对应元素 2048，$j=451$ 对应元素 2499；从 $j=452$ 开始超出逻辑范围。这个推导可以直接用于核对 mask、块指针 offset 和输出文件的有效长度。

地址计算中的 stride 以元素为单位，传入运行时的实际设备地址以字节表示。两者不能混用。把 BF16 的 stride 误乘一次 2，再交给按元素计算的块指针，会把相邻元素间隔扩大一倍。

### 指针张量与块指针

Triton 常见的访存表达有两种。指针张量逐个构造地址，通常使用 `tl.arange` 和 mask 描述有效位置；块指针把 shape、stride、offset 与 tile shape 组合起来，在 load/store 时指定需要检查的维度。

```python
offsets = tile_id * BLOCK + tl.arange(0, BLOCK)
valid = offsets < numel
x = tl.load(in1_ptr + offsets, mask=valid, other=0.0)
```

该片段展示指针张量形式的逻辑语义。完整上手示例采用块指针。两种形式都要表达真实的有效范围；支持的 rank、stride 和索引模式还取决于当前后端的降级能力，不能只根据 Python 能构造表达式就推断可运行。

块指针的 `boundary_check` 与指针张量的 `mask` 服务于各自接口形式。迁移时应按对应规则重建访存，避免把两套参数机械叠加。对连续一维数据，两种表达容易互相理解；对复杂 stride、gather 或索引张量，必须重新核对实际访问集合。

### Padding 值属于数值语义

尾部填充值会影响后续计算。逐元素加法在越界输出不写回的前提下，可以使用零填充；求和归约也通常以零作为无效元素的中性值。求最大值若直接用零填充，在所有有效值都是负数时就可能得到错误结果。

选择 padding 时，应从数学运算的中性元素推导。求和采用零；最大值需要不会大于任何有效输入的填充值，并且要核对当前数据类型与特殊值支持；乘法归约需要考虑一。没有通用的“零填充总是安全”规则。

边界检查还必须覆盖 store。读取时正确屏蔽越界元素，但保存时写满整个 tile，仍会破坏逻辑输出之后的内存。对多核切片，尾块写入不应越过本核拥有的输出范围。

### 二维矩阵与非连续输入

将一维推导扩展到二维时，tile 的起点变为 $(i_0,j_0)$，内部索引变为 $(u,v)$。元素地址由 $(i_0+u)s_0+(j_0+v)s_1$ 决定，同时需要满足行和列的有效范围。

以 shape 为 $(3,4)$、stride 为 $(6,1)$ 的矩阵为例，tile 内逻辑位置 $(1,2)$ 对应元素偏移 8，而不是连续矩阵中的偏移 6。若宿主封装先生成连续副本，kernel 可以继续使用连续布局，但这次复制的成本必须纳入算子或端到端测量。

上手例通过 `is_contiguous()` 检查明确限定连续输入。要支持非连续输入，可选择把 stride 作为显式参数传给经过验证的访存实现，或在宿主建立连续副本。两条路径具有不同的性能、别名和输出恢复要求，必须在接口文档中写清。

### 线性 tile 号展开为二维坐标

对输出 $C[M,N]$，设每个 tile 为 $B_M\times B_N$。行块数 $T_M=\lceil M/B_M\rceil$，列块数 $T_N=\lceil N/B_N\rceil$，总任务数为 $T_MT_N$。将线性 tile 号 t 按行展开时

$$
m_b=\lfloor t/T_N\rfloor,\qquad n_b=t\bmod T_N,
$$

起点为 $(m_bB_M,n_bB_N)$。先按商和余数分配 t，再在核内恢复二维坐标，即可复用一维分工。

取 $M=257$、$N=192$，tile 为 $128\times128$，得到 3 行块、2 列块，共 6 个任务。连续分配给两个核时，核 0 处理 t=0、1、2，核 1 处理 t=3、4、5。

| t | 行列块号 | 起点 | 有效输出形状 |
|---:|---|---|---|
| 0 | (0,0) | (0,0) | $128\times128$ |
| 1 | (0,1) | (0,128) | $128\times64$ |
| 2 | (1,0) | (128,0) | $128\times128$ |
| 3 | (1,1) | (128,128) | $128\times64$ |
| 4 | (2,0) | (256,0) | $1\times128$ |
| 5 | (2,1) | (256,128) | $1\times64$ |

Table: 非整除矩阵的二维 tile 展开

两核各有 3 个 tile，但有效输出元素分别为 40960 和 8384。这个例子再次说明，任务数量均衡与实际工作量均衡不同。更换展开顺序、tile 或分区可以改变这种差异，但每个方案仍要重新核对输出覆盖、LDG 分片和复用关系。

### Shape、tile 与输出分区

一个输出分区可以包含多个 tile，tile 又可能只有部分元素有效。不要用参与核数替代维度长度，也不要用 block 大小替代真实 row stride。建立测试时，应分别覆盖形状整除与不整除、tile 数整除与不整除、核数多于 tile 数三类情况。

例如，$N=2048$ 检查两个完整 tile；$N=2500$ 同时覆盖尾块和 tile 数不均分；$N=888$ 检查只有一个有工作核；$N=0$ 检查宿主空输入路径。它们各自检验不同的边界，不能互相替代。

## 任务分配与累加

### 每个输出元素的唯一写入者

基础向量加法让每个有效输出元素恰好由一个核、一个 tile 写出。所有核的输出区间并集应等于 $[0,N)$，任意两个区间的交集应为空。这个性质比“程序似乎能运行”更直接地解释正确性。

在一个独立的整除示例中，8 个完整 tile 可以分给两个核，各处理 4 个。图中每个 tile 的颜色代表唯一的输出归属；它用于说明归属规则，与贯穿案例的 2500 个元素使用不同任务规模。

![8 个完整 tile 的输出归属示意，每个区域只有一个写入核](assets/output-ownership.svg){width=100%}

当两个实例写同一个输出区域时，应先明确数学语义是否需要累加、覆盖或同步。多个普通 store 不会自动形成跨核归约。输出别名、共享中间量和原地更新都会改变依赖集合，需要重新检查安全性。

::: {.caution}
两个核的逻辑输出不重叠，还须检查它们是否共享同一个外部传输字。若部分字写入采用读改写，共享字内的不同小片也可能互相覆盖；分区与分配必须满足外部字独占和可读范围要求。
:::

基础示例使用独立分配和经过支持的边界路径。处理共享字或未对齐切片时，按[对齐与外部访问保证](#memory-api)补齐条件。

### 归约的范围与初始值

行归约把一行中的多个元素合并为一个或少量结果。若一行放在一个 tile 中，实例可装载整行、处理尾部后执行归约。若一行跨多个 tile，则需要在循环之间保存部分和或其他状态。

以求和为例，先将 BF16 输入提升到 FP32，建立 FP32 累加器，再对各块的部分和累加。初始值为零，最后完成全部有效元素后才转换或写回结果。每次进入循环都把累加器重置为零，会使输出只包含最后一块。

划分归约工作时，应区分两种情况。不同核处理不同的行，每一行拥有唯一写入者，可以自然独立执行；多个核共同处理同一行时，需要额外的部分和合并机制。第二种情况下，主 kernel 的局部和并不是最终输出。

### 矩阵乘的 K 循环

矩阵乘 $C=AB$ 中，M 与 N 决定输出位置，K 决定每个输出的累加范围。一个程序负责一个或多个输出 tile，在 K 方向循环读取分块，持续更新相同输出 tile 的累加器。

设输出 tile 为 $B_M\times B_N$，一次处理的 K 长度为 $B_K$。累加器在 K 循环外初始化；第 $k$ 块执行一次 `tl.dot` 更新；全部 K 块结束后，才应用输出转换或后处理，并把结果保存到它拥有的 M/N 区域。

若把 K 块作为彼此独立的输出任务，每个任务写同一块 C，就会丢失前面块的贡献或产生共享写入。只有显式设计 split-K 部分和存储与归约时，才能把这类任务独立分配。具体 Matmul 示例见[算子开发实例](#examples)。

以 K=384、$B_K=128$ 为例，三个块分别覆盖 $[0,128)$、$[128,256)$ 和 $[256,384)$。输出 tile 的生命周期贯穿三次更新。若原算法需要 FP32 累加，不能为了降低 L2 Buffer 占用，在每次更新后都转换成 BF16，再重新提升到 FP32；这会增加舍入节点，改变参考语义。

普通 `tl.dot` 的关键模式如下。`a_template` 和 `b_template` 已分别定位到当前输出块所需的 M 行与 N 行，K 起点为 0；二者的块形状分别是 $[B_M,B_K]$ 与 $[B_N,B_K]$，后者按 LDG 契约准备：

```python
acc = tl.zeros((BLOCK_M, BLOCK_N), dtype=tl.float32)
for k_block in range(total_k_blocks):
    k_start = k_block * BLOCK_K
    a_tile = tl.load(
        tl.advance(a_template, (0, k_start)),
        boundary_check=(0, 1), padding_option="zero",
    )
    b_nk = tl.load(
        tl.advance(b_template, (0, k_start)),
        memory_type="weight", boundary_check=(0, 1),
        padding_option="zero",
    )
    acc += tl.dot(a_tile, tl.trans(b_nk))
result = acc.to(tl.bfloat16)
```

该片段在循环内根据 `k_block` 更新两侧描述符，并把外部 FP32 累加器保留到全部 K 块完成。每次 `tl.dot` 产生本块乘积，再加到 `acc`；不要未经接口与目标配置核对，将它改写为带非零累加器的三参数 `tl.dot`。随后将 `result` 保存到本实例拥有的输出区域。模板建立、核间分区和输出边界采用随书 Matmul 示例的完整实现。

### 运行时标量与广播

向量加法中的 `alpha` 是一个标量。表达式 `alpha * z` 将它用于整个 tile，而不是把它当作同长度的输入张量。类似地，RMSNorm 的 `eps` 是标量，权重则通常是沿某一维广播的向量。把标量、长度为一的张量和广播向量区分清楚，有助于选择正确的参数类型和访存路径。

广播并不允许随意忽略 shape。张量维度的扩展方向必须符合运算定义，物理读取也必须遵循真实 stride。一个常见错误是将行缩放误写为列缩放，形状仍然可广播但数值完全改变。使用各行、各列数值不同的小输入可以较快发现这类问题。

例如 $X[2,3]$ 的两行分别乘 2 和 3，缩放值应扩展为 $[2,1]$；若要三列分别乘 2、3、4，则缩放值是 $[1,3]$。令 X 为全 1 可以检查广播方向，但不能同时检验原矩阵的索引。进一步将 X 各位置设为不同数值，才能同时检查读取与广播。

## 控制流、状态和数值类型

### 静态选择与运行时分支

当某个条件由 constexpr 决定时，编译器可以在特化阶段选择相应代码路径。运行时长度、索引或输入值决定的条件，则需要生成设备控制或选择逻辑。两者会产生不同的编译缓存行为，也可能带来不同的控制开销。

例如，是否启用一个固定后处理可以是特化选项；某个核本次分到零个 tile，则由运行时计算的循环次数决定。静态维度用于建立 tile shape，运行时有效长度用于边界判断。这种分工使同一个二进制能够处理多个合法输入长度，同时保留明确的静态工作集。

`tl.where` 表达值选择，不能当作短路控制来保护任意无效访问。将一个可能越界的 load 放在它的某个参数中，不能依赖“最终未选中该分支”来避免读取。访问保护应写在 mask、boundary_check 或合法的控制流中。

### 循环携带的状态

循环状态包括数值部分和内存部分。归约的部分和、在线 softmax 的最大值与归一化因子，是显式数值状态；同一个输出缓冲、循环写入的 KV 页和复用工作区，则形成内存状态。

初始化位置应对应数学范围。每个输出 tile 的累加器在其 K 循环前初始化，每个请求的注意力状态在该请求开始时初始化，缓存有效长度在实际更新完成后推进。把初始化放得过内会丢失历史贡献，放得过外会把上一行、上一 tile 或上一请求的状态带入下一份计算。

### 存储类型、计算类型与累加类型

BF16 输入不要求所有步骤都用 BF16。向量加法把输入提升到 FP32，计算后回写 BF16；归约通常需要单独确定累加类型；矩阵乘还要确定 PE 输出与跨 K 块累加的精度。每个转换节点都应与参考程序一致。

以三个标量 $a,b,c$ 的乘加为例，分别执行 FP32 乘法再加法，与一次融合乘加可能有不同的中间舍入；最后转 BF16 也不保证差异总被消除。精度检查先规定允许的输入域和运算顺序，再选择误差指标。不能仅凭输出 dtype 相同就判断两个实现等价。

状态更新还具有历史影响。一个 token 的 K/V 存储误差会被后续多个 query 使用，归约误差也可能通过后续非线性放大。验证既要检查当前输出，也要在复用状态的后续步骤检查结果。

### 小输入用于验证语义

编程模型中的规律可以用小输入单独验证。任务分配用 tile 编号作为数据，检查是否漏写或重写；矩阵索引用行列相关数值，检查转置和 stride；归约用全负输入检查最大值填充；KV 更新用与旧页不同的 token，检查只改变目标位置。

小输入的目的不是替代真实形状，而是让预期结果能被解释。通过后再覆盖更大形状、非整除边界、多个核和长序列。这样每个失败都能关联到具体语义，而不是只看到一个整体误差数字。

## 存算流水与执行单元映射

### 一个 tile 的生命周期

向量加法的 tile 依次经历装载、计算和写回；编译器据此安排暂存与同步。输入暂存须等最后一次计算读取结束，输出暂存须等写回读者结束，才能复用。若另一条计算链仍使用中间值，生命周期也必须覆盖该读者。分析流水时区分三类等待：计算等 load、下一次 load 等旧读者，以及 store 占用输出缓冲；三者需要不同的改进办法。

### 独立迭代与循环依赖

向量加法的不同 tile 没有数值递推；存储互不重叠、资源足够时，可以重叠部分工作。归约和矩阵乘的第 $k+1$ 次累加则依赖第 $k$ 次结果，提前装载下一块也不能消除该依赖。即使没有累加变量，复用输出、暂存或别名视图仍会形成内存依赖；只读同一份不变权重的两个循环则可以保持输出独立。

### 编译器选择与源码责任

核内并行的两种机制也需要区分。Multi-Executor 把一个逻辑操作的 tile 拆分给多个物理执行单元；Parallel-Executor 将多个独立逻辑操作或循环迭代放到不同执行单元。它们的工作粒度、数据归属和同步组织不同。看到多个 VP 工作并不能推断使用了哪种机制，应结合生成的 IR 和 trace 判断。
