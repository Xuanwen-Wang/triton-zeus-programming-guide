# 从 GPU Triton 迁移 {#migration}

迁移从保留算子的输入输出契约开始，再调整设备入口、任务映射与访存表达，最后进行平台相关调优。已有 GPU Triton 代码中的向量化表达、显式形状和分块思路可以继续使用；GPU 的启动 grid、线程组织、设备接口与调优参数则需要逐项核对。

本章以连续向量加法为最小例子。归约、Matmul 和融合沿用同一流程，但必须额外检查归约域、权重布局、中间精度与可见的原地更新。

## 迁移前检查

### 固定一个可以比较的原始版本

先保存原 kernel 的源码与代表输入，并写出数学定义、输入输出 shape、dtype、stride、允许别名、空输入和特殊值处理。已有实现如果依赖输入连续、维度可整除或某种对齐，应把这些条件移到接口说明和检查中。隐含条件最容易在迁移后变成静默错误。

原始 GPU 结果用于理解既有行为，同时保留一份独立数学参考。两者不一致时，先确认原实现采用的数值约定，例如分块累加、快速数学、低精度中间结果或特殊值处理。迁移目标应明确选择保留哪种契约，避免把“接近某个 GPU 输出”当作唯一正确性定义。

| 检查对象 | 迁移前要保存的信息 |
|---|---|
| 数据契约 | 数学公式、shape、stride、dtype、原地更新 |
| 特化 | constexpr、可选分支、配置选择条件 |
| 启动 | grid 计算、程序实例负责的工作区间 |
| 数值 | 累加精度、转换位置、近似函数与容差 |
| 集成 | 输出分配、执行流、同步、异常与缓存 |

### 识别 GPU 硬件假设

逐项检查 `num_warps`、`num_stages`、warp 相关布局、GPU 内联汇编、GPU 专用库和设备同步接口。它们与 GPU 后端的实现有关，不能仅因 Python 调用仍接受参数就推定在 Zeus 上有相同效果。对保留的选项，查看配套后端是否消费该选项以及怎样影响生成代码；对不适用的选项，从迁移后的基础配置中移除。

同样检查 atomic、异步拷贝、特定 cache modifier、descriptor 或 block pointer 组合的实际支持范围。支持判断应具体到 API、dtype、rank、布局和边界条件。一个简单例子编译通过，只能证明这一组合可进入相应路径，不能推广为任意组合都可用。

对矩阵乘，先区分逻辑矩阵 B 与权重存储对象。GPU 代码可能把 B 当作普通设备内存；本书示例使用核对应的权重地址表与权重装载路径。迁移时应把布局准备、权重生命周期和运行时参数一起纳入设计。仅把 `device="cuda"` 改为另一个名字，不能完成这部分转换。

### 把迁移项分成三类

第一类是数学表达与输出契约，例如向量加法、完整行归约、FP32 累加和可见 residual，迁移时应保留。第二类是程序映射与地址表达，例如 GPU 上每个 tile 一个 program、普通 B 指针、由取模表达的边界，需要按 Zeus 执行与存储模型改写。第三类是调优策略，例如 warp 数、软件流水深度和特定 cache hint，需要在新平台重新选择。

| GPU 实现中的内容 | Zeus 迁移时的动作 |
|---|---|
| 算子公式与可见输出 | 保留，并把隐含转换写清楚 |
| `grid=ceil(N/BLOCK)` | 对照运行时核数入口，改成核内循环 |
| 原始 stride 与转置视图 | 显式描述或在 Host 连续化 |
| 普通 B 权重张量 | 按消费者方向创建配套 LDG 存储 |
| warp/stage 调优组合 | 重新选择 tile、Parallel 和双缓冲 |
| 原子归约或共享写入 | 重新设计输出所有权及合并阶段 |

Table: 保留语义、重写映射与重新调优

这张表不是 API 名称的一一替换。特别是 `num_warps` 与 Parallel 宽度，前者在 GPU 描述线程组织，后者在 Zeus 放置多个独立逻辑操作，不能用相同数值表示相同并行度。普通权重指针与 LDG 描述对象也不只是参数类型不同，它们携带的布局和核所属关系不同。

## 最小改写与回归

### 先迁移单核向量加法

常见 GPU 写法让每个 program 负责一个 tile，启动 grid 为 `ceil(N/BLOCK)`。核心地址计算如下。

```python
tile = tl.program_id(0)
offsets = tile * BLOCK + tl.arange(0, BLOCK)
x = tl.load(x_ptr + offsets, mask=offsets < N, other=0)
z = tl.load(z_ptr + offsets, mask=offsets < N, other=0)
y = (x.to(tl.float32) + z.to(tl.float32)).to(tl.bfloat16)
tl.store(y_ptr + offsets, y, mask=offsets < N)
```

这个片段表达了正确的逻辑 tile 切分。但在本书配套的 Zeus Python 启动适配中，`grid[0]` 用于选择核数；把大型向量的 tile 数直接作为核数并不符合该入口的约定。迁移后的 kernel 按核分工，并在核内循环处理多个 tile。

先设置 `CORE_NUM=1`，把所有 tile 放入一个实例的循环。再用块指针表达整体形状与当前 tile 的偏移。块指针的边界检查替代片段中的逐元素 mask，输入的越界位置填零，输出仅写入合法范围。

```python
template = tl.make_block_ptr(
    base=x_ptr, shape=(N,), strides=(1,), offsets=(0,),
    block_shape=(BLOCK,), order=(0,),
)
for tile in range(tl.cdiv(N, BLOCK)):
    block_ptr = tl.advance(template, (tile * BLOCK,))
    x = tl.load(block_ptr, boundary_check=(0,),
                padding_option="zero")
```

这段片段只展示 X 的读取；完整向量加法同时建立 X、Z、Y 的块指针，并使用[第一个向量加法](#vector-add)的 FP32 计算与 BF16 输出。先在 `N=1`、`1024`、`1025`、`2500` 上验证单核路径。每个输出元素应恰好写一次，空输入由宿主封装直接返回。

### 再引入双核任务分配

单核结果稳定后，采用[向量加法实例](#vector-add-tuning)的连续均分规则，将 tile 分配到两个核。启动 grid 为 `(CORE_NUM,)`，`CORE_NUM` 与实际设备和编译配置一致。kernel 内的 `tl.program_id(0)` 得到当前实例编号，用来确定自己的起始 tile 与循环次数。

对 `N=2500,BLOCK=1024`，core 0 写前两个 tile，core 1 写最后一个 tile。对 `N=888`，core 1 不处理任何 tile。无工作核应正常完成且不写入输出；这是核数多于逻辑工作项时的必要边界。

多核不应改变数值契约。向量元素之间互不依赖，因此每个元素的计算过程可以保持不变。行归约采用按行分工时，也可以让每个核持有完整归约域。Matmul 按 N 切分时，每个核仍计算完整 K 累加；按 K 切分则需要合并部分和，浮点加法顺序也会变化，必须单独验证。

### 保持无工作核的合法行为

GPU 代码常用 grid 数量刚好覆盖有效 tile；Zeus 的固定核数入口则可能启动没有工作可做的核。对一个小于 BLOCK 的向量，core 1 的循环次数应为零。循环外若存在与 tile 相关的装载、输出初始化或共享写入，就仍可能访问不属于该核的数据。

迁移时把核私有的起点与循环次数计算清楚，数据装载放在相应的工作范围内。若引入核间协作，必须另外检查无工作核是否需要参与该协作，不能因为循环为空就省略另一核等待的同步动作。最小的单 tile 输入和核数大于工作项数量的情况，能直接暴露这类问题。

## 访存表达的迁移

### 移除取模时补齐真实边界

某些 GPU Matmul 模板使用 `row = raw_row % M`，将 M 尾部的多余行重新映射到已有行，再在输出阶段屏蔽。这个写法在 GPU 上可能服务于特定布局和连续性优化；在 Zeus 上，则可能让地址分析需要处理额外的回绕。

假设 `M=130,BLOCK_M=128`，第二个 M tile 的原始行号是 128–255。取模后会访问行 128、129、0、1……125。移除 `% M` 后，有效行只剩 128 和 129，其余输入必须由边界检查填零。只删取模、保留原来仅检查 K 的 load mask，会直接访问 M 范围之外。

迁移为块指针时，把 `shape=(M,K)` 和 `block_shape=(B_M,B_K)` 分开；移动位置为 `(m0,k0)`，装载同时检查两个维度。对于普通指针表达式，则应同时构造 M/K 两个维度的 mask。两种写法都能表达相同有效域，不应混合一半规则而遗漏某个边界。

```python
a_block = tl.make_block_ptr(
    base=a_ptr, shape=(M, K), strides=(K, 1),
    offsets=(0, 0), block_shape=(B_M, B_K), order=(1, 0),
)
a = tl.load(tl.advance(a_block, (m0, k0)),
            boundary_check=(0, 1), padding_option="zero")
```

输出只写有效 M/N 元素，K 尾部的无效输入则填零。这个组合保留了矩阵乘的数学定义，同时让规则矩形直接出现在描述符中。

### 不把 `tl.where` 当作访存保护

下面的思路是错误的：先从 `ptr+offsets` 无条件装载，再用 `tl.where(offsets<N,value,0)` 把无效结果替换成零。选择发生时，非法读取已经可能执行。正确方法是在 load 上添加有效域，或使用带真实 shape 和 `boundary_check` 的块指针。

同理，`tl.where` 不能自动让无效分支中的除法、指数或指针操作免于求值。对 softmax 的 mask，要同时考虑访存合法性和数学有效域；对空归约，要在接口中定义分母与输出。把 GPU 上恰好没有报错的表达式原样搬过来，不能作为范围安全的依据。

### 处理动态 stride 与广播视图

先把真正需要支持的布局写成有限集合。若业务只提供连续 `[M,H]` 张量，入口直接检查连续性是合理的；若必须支持转置、切片或广播，kernel 的真实 stride、零步长和别名行为都应成为接口的一部分。不能为了让编译器看见常量，就把运行时 stride 强行写成连续布局。

对于始终固定的布局，可以让必要的 stride 或维度成为编译期参数，以便生成规则描述符；代价是可能增加特化产物。对于经常变化的值，保留动态参数并使用配套后端支持的表达，或者由 Host 在少量稳定布局之间选择。特化键与缓存行为以实际 Zeus JIT 入口为准，不从其他 Triton 后端文档推定每个整数值都会触发同样的编译。

广播输入常通过 stride=0 表示多个逻辑位置共享同一个值。它与多个输出位置指向同一个可写地址完全不同：前者可能是合法只读复用，后者涉及写冲突。迁移时明确只读权重的广播轴，以及输出是否拥有独立存储；若当前路径无法表达某种广播视图，可在 Host 有意识地物化，并计算这次分配与拷贝成本。

## 矩阵乘与缓存的迁移

### 将逻辑 B 转为匹配消费者的 W

GPU GEMM 常接收 `B[K,N]` 及其 stride。普通 Zeus weight 路径可以采用 `W[N,K]`，满足 `W=B.T`。Host 应先完成逻辑转置并得到连续 W，再按目标 LDG 格式打包；kernel 读取 `[B_N,B_K]` 并以 `tl.trans` 参与 dot。逻辑转置、打包和 kernel 中的维度交换分别承担不同职责，不能凭看到两个“转置”就删除其中一个。

例如 B 为 `[384,256]`，W 应为 `[256,384]`。如果直接把 B 的连续字节按 W 形状交给打包器，元素总量一致，内容却不是转置矩阵。用 A 的单个 K 位置为一的测试，可以检查输出是否对应 B 的正确一行；这种结构化输入比单次随机误差更容易定位。

在双核按 N 分区时，Host 分别打包 W 的不同输出行段。kernel 的本地 N 坐标从零开始，C 的全局 N 起点另加核分区偏移。权重描述对象需要持有各核分配的生命周期；不能用普通张量 `data_ptr()` 临时拼出一个看似相同的地址表，绕过格式和所有权。

### 保留完整 K 累加

GPU 实现可能依赖特定 dot 输入精度、快速数学选项或低精度累加。迁移时显式确定输入 dtype、dot 累加 dtype、K 分块和输出转换位置。BF16 输入提升后的参考与原始 FP32 输入的参考并不相同；每个 K 块后转回 BF16，也不等于全部 K 完成后转换一次。

如果原 GPU 实现用 split-K 和 atomic 合并部分和，可以先迁移为一个核持有完整 K 的版本，再评估是否值得重新引入拆分。这样能够先隔离矩阵乘本身与跨核合并。重新引入合并时，要设计 FP32 部分和存储、初始化、同步和最终输出转换，不能仅把 atomic 调用替换成普通 store。

### 缓存迁移以布局为单位

一个 KV Cache 格式至少包括：逻辑张量轴顺序、物理块布局、dtype、量化 scale、页长、页表含义、核分区与更新方式。迁移缓存时，让 producer、store、load、attention consumer 使用同一份格式定义。只修改 attention 的 load，往往会读取到按照旧布局写入的数据。

本书的普通 weight GQA 路径使用 K `[R,D]`、V `[D,R]`，以及普通 int32 逻辑页表和每核 LDG 基址对象；专用 `kcache/vcache` 路径采用另一组描述符和索引表。二者都能表达 KV 的数学含义，但不能共享原始物理字节。路径选择和完整坐标示例见[分页 KV Cache 与 Attention](#attention-cache)。

对量化缓存，还要确认 scale 的粒度、所在位置与生命周期。逐 token、逐组或逐页 scale 不能只凭 dtype 相同就互换；新增 token 的数据和 scale 也应在消费者读取前共同更新。迁移测试先检查缓存写回，再检查 attention 输出，能避免把布局错误误判为量化误差。

## 数值与归约结构的迁移

### 保持归约域完整

从“一 program 一行”改为“一核处理多行”时，每一行仍要归约完整 H。若把 H 切成多个 tile，则必须明确采用整行驻留、两遍读取或跨块递推；不能让每个 tile 各自归一化，再拼接结果。RMSNorm 的分母使用真实 H，softmax 的分母只包含有效元素，这些语义与 tile 大小无关。

归约轴变化也需要重新检查形状。`tl.sum(x,axis=1)` 得到每行的统计量，保留维度时为 `[B_R,1]`；沿 axis=0 则得到每列统计量。依靠小尺寸 `1×H` 的单行用例，无法证明多行广播正确。至少增加两行不同输入，并检查每行统计量没有相互混用。

### 不提前删除低精度转换

两个 GPU kernel 之间通常存在一个低精度张量。把它们融合为一个 Zeus kernel 后，这次外存写回可以省去，但可见数值契约中的低精度转换不一定能删。Fused Add RMSNorm 就需要先把 residual 转 BF16，再提升到 FP32 求平方和。

判断转换能否删除，应问它是否改变了下一步实际读取的值，而不是问是否还有外存张量。如果原契约明确允许使用更高精度中间值，可以把这种变化作为独立算法版本；否则保持转换并检查编译结果。对多个输出，逐个确认 dtype、别名和舍入位置，不能只比较最终主输出。

### 区分正常输入与特殊值

指数、除法、rsqrt、饱和或近似模式可能具有平台相关细节。先明确业务输入范围，并比较常规有限值；再单独测试零、极小值、极大值、NaN、Inf 与带符号零。不能由“同一行随机输入接近”推出所有特殊值行为一致。

对于近似函数，既保留独立数学参考，也保留使用相同转换位置的实现参考。如果只与旧 GPU 输出比较，可能把旧实现的误差固化为唯一目标；如果只与无限精度公式比较，又可能忽略双方契约中允许的 BF16 转换。误差预算应在性能调参之前确定，并保存差异位置和随形状变化的趋势。

## 宿主与框架接入

### 调整宿主入口和参数生命周期

宿主侧负责导入配套后端、创建正确设备上的张量、分配输出、传入标量和常量，并在结果需要被 CPU 使用前完成同步。保留[编译、执行与框架接入](#compile-and-run)的配套入口，不把 GPU 的设备事件或同步调用留在 Zeus 路径中。运行时按[后端配置](#runtime-backends)连接功能模拟或物理设备；两者使用相同的 JIT 提交形式，但测试报告需要注明实际后端。

调用封装还应检查输入 shape、dtype、stride 与可见输出。对连续张量示例，非连续输入可以明确拒绝，或由上层选择一次连续化；若选择连续化，需要说明额外分配和拷贝，并在端到端性能中计入它们。不要在 kernel 内默默按连续布局处理非连续张量。

对 JIT 与 AOT，分别确认哪些值属于运行时参数，哪些值形成编译特化。`BLOCK`、核数和选择实现路径的 constexpr 会影响产物匹配；动态长度与指针按参数 ABI 传入。修改常量后应确认实际使用了相应产物，不能仅根据缓存目录中的文件名判断。

Host 的整数张量也要显式指定类型。页表或 slot 接口声明 int32 时，使用默认 int64 的 `torch.tensor` 或 `torch.arange` 可能产生不匹配；但把所有 int64 一律改为 int32 又可能溢出。应先检查合法值范围，并区分 token 编号、元素偏移、字节偏移和指针地址。指针不能因为索引使用 int32 就截成 32 位。

对长寿命权重、页池和 scratch，确定 owner 的存活范围。对原地输出，确认后续调用者使用的是更新值，仍需要旧值的路径已保存副本。对异步执行，释放和复用发生在相关工作完成之后。对 Graph，提前创建稳定缓冲，再更新内容；测试时连续执行不同数据，而不只是重复相同输入。

### 分别完成算子与框架回归

算子回归比较固定输入下的输出；框架回归还检查调用前后的张量、输出存储、原地更新与执行顺序。一个脱离框架的 kernel 通过，不足以证明注册、缓存、生命周期和模型调用均正确。

先完成单独调用，再重复调用，再加入与前后算子的组合。对多输出和原地算子，确认调用者读到的是约定的新值，旧输入如果仍被后续使用则必须保留。对动态形状，切换形状后重新检查特化与产物匹配，不能只测试单一形状的多次重复。

性能比较放在正确性与集成稳定之后。先报告原 GPU 环境和 Zeus 环境各自的配置与计时边界，再报告各平台上的优化前后对照。跨平台硬件、带宽与运行时不同，某个源码结构在 GPU 上更快，不能直接作为 Zeus 的默认选择依据。

### 形成可维护的迁移结果

迁移完成的交付物包括 kernel、宿主封装、独立参考、代表输入集合和运行说明。配置选择集中管理，每个条件有对应测试；平台差异集中在明确的位置，避免在数学表达中散落设备分支。需要特定工具链版本的接口，在版本配套和支持表中注明。

后续升级编译器或 SDK 时，先重放原始回归集合，再比较新产物与性能。原先验证过的源码不会自动为新二进制提供正确性保证；反过来，单一新版本的性能变化也不能直接归因于源码。分别记录 kernel 与工具链身份，可以让迁移结果在迭代中保持可解释、可复现。
