# 性能分析与调优 {#performance}

调优从一份正确、可复现的基线开始。每轮改动先提出可以验证的假设，例如“尾块使两核工作量不均衡”或“下一块数据到达得太晚”；再用输出比较和时间线检验。只看总耗时，难以区分 kernel 写法、编译器选项、缓存与运行环境各自带来的影响。

本章以向量加法说明流量和任务分配，以归约说明数据复用，以 Matmul 说明存算流水。示意图中的方块表示依赖关系和相对顺序，不代表某一设备的实测周期。

## 基线、计时范围与瓶颈

### 分开测量编译、kernel 与调用链

首次调用可能包含 Python 导入、特化、编译、二进制装载和实际执行。热态 kernel 测量应在编译与装载完成后进行。端到端测量则按业务边界包含必要的参数准备、调度、数据转换和同步。三个数各有用途，报告时明确给出计时区间。

设备执行通常具有异步性。宿主提交返回不等于设备完成；在宿主用时钟测量时，必须用配套运行时的同步方法闭合测量区间。若采用设备事件，则确认事件所在执行流、记录位置与计时单位。不同计时方法应分别形成基线，不能直接把同步后的宿主墙钟时间与单条设备指令时长比较。

推荐先进行若干次预热，观察耗时是否稳定，再采集多次运行。记录中位数与分位数，保留原始样本。测量很短的 kernel 时，可以在一次同步区间中连续运行多次，再除以次数；该方法反映连续提交下的平均时间，报告中应同时说明批量次数。原地算子需要在每次独立样本之前恢复输入，避免后续样本计算的是不断变化的数据。

| 对照项 | 必须固定的内容 |
|---|---|
| 输入与数学语义 | shape、dtype、stride、量化、随机输入与容差 |
| 编译产物 | kernel 源码、特化常量、编译器与选项 |
| 执行环境 | 设备或仿真器、运行时、时钟与并发负载 |
| 测量方法 | 预热、同步、重复次数、统计量和计时边界 |

Table: 一次性能对照的固定条件

### 从工作量估算瓶颈方向

BF16 向量加法对每个元素读取两个 2 字节输入，写出一个 2 字节输出。不计对齐、缓存与额外搬运时，逻辑外存流量为 $6N$ 字节。`numel=2500` 时是 15000 字节；实际总线流量可能因搬运粒度和尾块而更大。以逻辑流量除以设备 kernel 时间得到“有效带宽”，报告名称应保留“有效”二字。

$$
B_{\mathrm{effective}}=\frac{6N}{T_{\mathrm{kernel}}}.
$$

当 $\alpha=1$ 时，数学定义只有一次加法；运行时标量乘法是否被消除取决于编译器是否能证明它等于一。因此估算计算量时，应区分数学操作数与实际生成的操作。改变 `alpha` 的特化方式也可能改变编译结果，不能在没有说明的情况下当作纯 tile 调整。

对一般算子，可以用计算量 $F$、外存字节数 $Q$、相同 dtype 下的可用吞吐 $P$ 与带宽 $B$ 估计理想下界。

$$
T_{\mathrm{ideal}}\geq
\max\left(\frac{F}{P},\frac{Q}{B}\right).
$$

这个估算帮助选择优化方向。真实 kernel 还包含启动、搬运指令、同步、依赖链和尾部开销。峰值规格必须与实际 dtype 组合、核数、时钟和统计范围匹配；在这些条件未对齐时，先使用同条件 A/B 耗时与时间线进行判断。

### 沿关键路径读时间线

先找到整个 kernel 的完成区间，再观察关键路径上的连续工作和空白。对双核执行，分别记录每个核自己的开始与结束，计算各核时长，并报告最大值；若使用全局统一时间轴，也可另报从最早开始到最晚完成的包络区间。二者定义不同，不能混用。

观察 VP、PE、DT 和搬运相关单元时，关注三类信息：某个单元实际工作的区间、等待所依赖数据的区间、最后一块工作完成后其他单元仍在运行的尾部。trace 中出现多条不同 lane 的指令，只说明使用了这些 lane；只有工作区间重叠，才说明发生了并行。

统计 busy 时间时，对同一资源的区间求并集。指令记录的开始和结束语义可能覆盖发射、排队或内部处理，相邻指令区间也可能重叠。简单把所有持续时间相加，会把重叠部分重复计算。需要给“利用率”时，同时写清分子与分母，例如某单元忙碌区间并集除以 kernel 完成区间。

## 任务切分与访存效率

### 分别判断 VP、PE、DT 和数据访问路径

Zeus 上的一个算子往往包含多种执行资源。Matmul 的主要乘积在 PE 上完成，归约、指数、逐元素变换主要涉及 VP，布局转换可能涉及 DT，GDG 与 LDG 则提供不同来源的数据。调优对象应是最终完成时间上的瓶颈，不能把所有非 PE 时间都视为可以删掉的开销。

| 时间线上的现象 | 首先核对的依赖 | 可尝试的改写 |
|---|---|---|
| PE 每个 K 块前都有空白 | 对应 A、W 是否已就绪 | 增大搬运粒度或提前装载 |
| PE 连续，VP 集中在结尾 | epilogue、归约或转换 | 合并可融合的逐元素步骤 |
| DT 活跃，PE 等待 | 转置是否物化、谁消费它 | 改变存储方向以减少转换 |
| VP 多 lane 仍串行 | 数据依赖、共享写入、输入就绪 | 暴露独立工作并减少别名 |
| 所有单元短促且间隔大 | Host 提交、描述符、标量循环 | 合并小工作项、核内循环 |
| 一核完成后另一核很长 | 各核有效工作量 | 调整块大小或分区 |

Table: 由资源现象选择下一项检查

读 PE 空白时，沿该次计算向前找两路输入。A 往往来自 GDG 装载或上一算子，W 可能来自 LDG；这两路都完成后才能开始计算。若 A 已经就绪而 W 的 LDG 读取尚未完成，继续增加 A 的预取深度通常无助于该空白。反之，W 已到达但 A 因上一轮缓冲占用不能装载，则应检查 A 的生命周期和双缓冲容量。

读 VP 空白时，区分“没有足够的独立运算”和“独立运算有了但输入未到”。RMSNorm 的平方和与逆平方根存在顺序依赖，不能让后者越过前者；不同完整行之间则可以独立。在线 attention 的同一 head 的序列块也有 `m/l/o` 递推依赖，而不同 head 在输入输出不重叠时可能独立。选错并行维度会在源码中增加展开，却无法缩短关键路径。

读 DT 活跃时，先确认它在做实际布局变换，还是为了满足某个算子的输入格式而搬移已有数据。同一个逻辑转置，如果能够通过消费者的描述符表达，就可能无需独立转换；如果 Host 原始布局与目标矩阵运算方向不一致，DT 工作可能是必要的。此时可以把转换前移到权重初始化阶段，但不能把前移的成本当作完全消失。

### 先检查每个实例分到多少工作

贯穿案例中 `numel=2500`、`BLOCK=1024`，共有三个 tile。按照连续均分策略，core 0 处理两个 tile，core 1 处理一个尾 tile；两个核分别承担 2048 和 452 个有效元素。即使两个核都已启动，工作量仍然不均衡。较小的 tile 可以改善分配粒度，但会增加循环、描述符和边界处理开销。

因此 tile 大小的选择应覆盖小输入、整块、多块和尾块几种代表场景。每个候选都先通过正确性测试，再检查两核的实际工作区间。若一个配置改善长向量却损害小向量，可以按明确的 shape 条件保留不同配置；条件必须可测试，不能依赖偶然的输入值。

分工还应保证输出所有权唯一。向量加法每个 tile 写独立区间，行归约每个行块写独立行，切 N 的 Matmul 每个核写独立列区间。这类切分可以避免额外的结果合并。切 K 则让不同核产生同一输出的部分和，需要显式合并、额外存储或同步，应把这些成本一并计入。

### 连续访问与有效载荷

连续布局让相邻元素靠近，有利于较大粒度的搬运。跨步视图可能只利用每次搬运的一部分字节，或要求额外的数据整理。评估布局变换时，要比较两种完整路径：直接处理非连续输入，以及先转换为连续布局再执行。只有把转换和临时存储成本计入，才能判断整条调用链是否获益。

尾部 padding 也会影响有效载荷。`BLOCK=1024` 的最后一个 tile 只有 452 个有效元素时，计算或片上处理仍可能按完整 tile 形状展开。边界检查保证合法访问，未必把所有无效元素的处理成本消除。可从编译 IR、描述符与 trace 确认实际行为，再决定是否为小尾块增加专门路径。

### 用复用减少重复搬运

RMSNorm 的同一行需要参与平方和与归一化。如果整行能留在 L2 Buffer，归约完成后可以直接使用已装载的数据。若列方向必须分块，在全部列的平方和得到之前无法完成归一化，通常需要重新读取、保存中间数据或重计算。选择哪条路径，取决于行宽、可用容量及搬运成本。

Matmul 中，一个 A tile 可以参与多个输出列块，一个权重 tile 可以参与多个输出行块。调整循环次序会改变复用机会，也会改变同时存活的累加器数量。增加复用的同时，应检查 L2 Buffer 是否足够、活跃时间是否过长、编译器是否因此插入额外搬运。只减少源码中的 `tl.load` 次数，不足以证明最终外存流量减少。

## L2 Buffer 工作集与 tile 选择 {#working-set}

### 按同时存活的张量计算

估算工作集时，从逻辑张量体积开始，再检查编译后的物理大小。输入 BF16 并不意味着所有中间量都按两字节保存：FP32 归约、累加器、转换结果和临时广播都可能同时存活。双缓冲与多个独立 lane 还会引入更多副本。

以 `BLOCK_M=BLOCK_N=BLOCK_K=128` 的 BF16 Matmul 为例，L2 Buffer 活跃量与 LDG 读取量分开计算。表中 KiB 按 1024 字节计算。

| 张量与所在路径 | 形状与类型 | 逻辑体积 |
|---|---|---:|
| L2 Buffer 中的 A tile | `128×128 BF16` | 32 KiB |
| L2 Buffer 中的累加器 | `128×128 FP32` | 64 KiB |
| 主要活跃量合计 | A 与一个累加器 | 96 KiB |
| LDG 的 W 读取块 | `128×128 BF16` | 另计 32 KiB |

Table: 分开计算 GEMM 的 L2 Buffer 工作集与 LDG 读取量

给 A 保留 ping/pong 两份时，L2 Buffer 主要活跃量变为 `2×32+64=128 KiB`。如果一份 A 同时用于两个 N 块，则有两个累加器，主要活跃量为 `32+128=160 KiB`；再给 A 双缓冲，是 `64+128=192 KiB`。两个 N 块对应的 W 共 64 KiB，属于 LDG 读取和复用的数据体积，不能直接加进 L2 Buffer 预算，也不默认给 W 分配一套 L2 Buffer 双缓冲。

这些计算用于筛选候选，不是实际地址分配报告。如果某条实现确实把权重物化、转换或暂存到 L2 Buffer，再把对应缓冲按其物理大小与生命周期加入。经 LDG/WL1 读取的 W 与普通激活 tile 走不同的数据路径，是 Zeus 工作集分析需要保留的区别。

本书配套 Zeus V3 编译目标的 L2 Buffer 总量为 512 KiB，最高 1 KiB 为持久通信标志保留；栈空间、对齐、布局 padding 和编译器临时量还会影响可分配空间。因此“主要张量相加小于 512 KiB”只是必要的粗筛，不是编译成功的充分条件。实际容量判断以所用编译目标及地址分配结果为准，不把这些数值外推到其他硬件型号。

### 区分容量浪费和算力浪费

tile 太大有两种代价。第一种是 L2 Buffer 工作集变大；第二种是尾块的无效区域变多。假设输出矩阵有 65 行、129 列，用 `128×128` 输出 tile，则逻辑输出只有 8385 个元素，按 tile 覆盖的矩形却有 `128×256=32768` 个位置。边界检查阻止越界写入，但不能据此断言内部乘积只计算 8385 个位置。

对一组 `M,N,K` 和 `B_M,B_N,B_K`，可以先计算理想填充效率：

$$
\eta_{\mathrm{tile}}=
\frac{MNK}{
\lceil M/B_M\rceil B_M\,
\lceil N/B_N\rceil B_N\,
\lceil K/B_K\rceil B_K}.
$$

该比值把实际维度与按完整矩形覆盖的工作量进行比较，不是硬件利用率。如果后端有更细的有效范围裁剪，实际浪费可能小于该模型；如果额外布局转换和数据访问开销明显，整体时间也可能比该比值预期的更差。它的作用是及早发现“用长序列、大 batch 配置处理极小输入”的明显不匹配。

缩小一个维度时，应知道自己解决什么问题。减小 `BLOCK_M` 通常减小 A 和输出累加器；减小 `BLOCK_N` 通常减小 W 和输出累加器；减小 `BLOCK_K` 减少单轮输入体积，却增加 K 循环次数。K 维累加器的形状不随 `BLOCK_K` 变化，因此资源主要被累加器占用时，仅减小 `BLOCK_K` 可能没有预期效果。

### RMSNorm 的预算为什么容易低估

一个 `B_R×B_H` 行块同时可能需要 BF16 输入、提升后的 FP32 值、平方结果、行统计量、权重和输出。若只按输入字节数计算，`4×8192×2=64 KiB` 看似很小；一份同形状 FP32 中间量却是 128 KiB。几份这样的中间量同时存在，就接近目标容量。

不要直接把所有源码中出现过的张量体积相加，因为编译器可能融合或复用；也不要只计算最大单个变量。正确方法是画出生成值到最后一次使用之间的区间，对同一时刻存活的物理缓冲求和。归约以后仍要使用原始 X 完成归一化，这使 X 的生命周期跨越整个平方和计算；列分块两遍算法正是通过重新读取 X，缩短这段驻留需求。

优先尝试把每次处理的行数从 4 改成 2 或 1，保持整行归约；如果单行仍然过宽，再改成列分块。这样可以分别观察“并行行数”和“归约算法”两个因素，避免一次调整过多维度。两遍算法的读流量增加是明确的，而 L2 Buffer 峰值是否足够下降，需要看实际编译报告。

## LDG 访问、布局与打包 {#ldg-performance}

### 从消费者的矩阵方向选择布局

LDG 是 Zeus 的近存 DRAM，可保存权重和 KV Cache，并通过专用通路参与矩阵运算。API 中的 `memory_type="weight"` 是一条具体读写路径的名字，不表示 LDG 只能保存静态模型权重。布局设计必须同时满足生产者写入和消费者读取。

对于 $C=A W^T$，A 为 `[M,K]`，W 为 `[N,K]`。W 的逻辑内层为 K，实际连续段由打包格式决定；读入 `[BLOCK_N,BLOCK_K]` 后通过逻辑转置参与 dot。对于 decode attention，QK 需要按 token 取 K 的完整 D 维，而 PV 需要沿 token 求和。普通 weight 路径因而可以把 K 保存为 `[R,D]`，V 保存为 `[D,R]`，使两个 dot 都采用各自的 weight 描述符。代价是新 token 的 K 是行写入，V 是列写入，更新方法必须随之改变。

专用 `kcache/vcache` 路径使用自己的页表与布局契约，不能把普通 weight 路径的矩阵形状、偏移公式和指针表直接套用过去。选择路径后，打包器、更新 kernel 和读取 kernel 应当作为一组共同设计；切换其中一个而保留另两个，是缓存数据静默错位的常见原因。

### 对齐同时涉及基址、行段和块边界

本书普通 BF16 weight 示例采用 `Tr=Tc=1` 时，一个物理块为 128 行、每行 64 个 BF16 元素，总计 16 KiB。逻辑矩阵先按这种块划分，块内部行主序。因而一个逻辑 256 元素长的行，横跨四个物理块中的四个 64 元素行段，不能把它理解为从 LDG base 起连续的 512 字节。

这解释了为什么“数据字节总量正确”不等于“布局正确”。以逻辑 `[256,256]` BF16 矩阵为例，元素总量为 128 KiB；简单连续拷贝和按块打包的总字节数可以一样，但矩阵的第二个 64 元素行段位于不同地址。应先用小矩阵核对块内、块间、行块边界，再扩大到完整权重。

`Tr/Tc` 进一步组织多个物理块形成 patch。改变 patch 几何会改变块之间的存放次序和 padding，相关读写描述符必须一致。不要把某个 dtype 和 patch 的最优参数视为通用对齐规则。矩阵维度不整齐时，区分“物理存储补齐”与“数学上的有效 K”；补齐部分必须按消费者需要初始化，不能参与真实归约。

### 计算每轮读取量与复用

对一个输出 tile 的 K 循环，不考虑复用时，每个 K 块读取 `2 B_M B_K` 字节 A 和 `2 B_N B_K` 字节 W，完成约 `2 B_M B_N B_K` 次浮点运算。两路输入的复用方向不同：增大 M 使每个 W 元素服务更多输出行，增大 N 使每个 A 元素服务更多输出列。若 M 很小，W 的有效复用低，增加 N 还会增大输出累加器与每轮权重读取量，应结合实际 LDG 带宽和计算瓶颈选择。

以 `M=N=256,K=384`、三个块维度均为 128 为例，基础三重循环有 4 个输出 tile，每个 tile 3 次 dot，共 12 次 dot。A 沿 M 方向有 2 块、沿 K 方向有 3 块，共 6 个不同 tile，却会因两个 N 块各读一次而形成 12 次源码级装载；W 也因两个 M 块而类似重复。将两个 N 块放在同一个 K 循环中，可以让 A 的源码级装载从 12 次减到 6 次，但要同时维持两个输出累加器。

![复用一个 A tile 时的两个输出累加器](assets/matmul-reuse.svg){width=100%}

重排以后继续确认生成代码是否保留了这种复用，是否因 L2 Buffer 压力又重新装载，以及 LDG 权重读取或 FP32 累加是否成为新的关键路径。初始化阶段的权重打包也应单独计时：对长期复用的模型权重可摊薄，对每次都变化的短寿命矩阵，则可能成为调用链主要成本。

### 让搬运描述符保持规则

连续大块、固定跨度的矩形，通常比逐元素的动态地址更容易表达为规则搬运。若访问本来是规则二维矩阵，就保留二维 shape、stride 和两个维度的边界；不要先展平成复杂取模，再期待编译器重新发现原来的矩形。

例如 GPU 模板中 `row = raw_row % M` 会把尾部行重新映射到前面几行。移除取模时必须同时补上真实的行边界保护，不能只删 `% M`。对于页缓存，每个序列块只在一个页内时，先读取一个物理页号，再建立规则块地址；如果块跨页，应拆块或明确支持多页映射，不能用一个页号解释两个不同物理页。

如果块访问很小，描述符设置、循环和指令提交的固定成本可能超过实际数据计算。此时先把相邻小块合并成一个连续 tile，或把规则多行表达为一次块操作。增加 tile 之后仍需重新检查 L2 Buffer 占用和尾部效率；提高有效载荷与降低工作集压力，是同一次调参中的两端。

## 存算重叠、流水与双缓冲

### 从一个 tile 的生命周期开始

顺序执行时，一个 tile 依次经历输入搬运、计算和输出写回。流水希望在 tile $i$ 计算时提前搬入 tile $i+1$，并在依赖允许时写回 tile $i-1$。允许重叠的前提是它们使用的资源与缓冲区不存在冲突，同时满足数据依赖。

![顺序执行与使用两个缓冲槽的流水](assets/performance-timeline.svg){width=100%}

图中的 ping 与 pong 是两个交替使用的缓冲槽。槽位重新用于搬入新数据之前，上一轮使用它的计算必须已经完成；输出写回读取的缓冲也必须保持有效直到写回结束。“输入已到达”和“缓冲可重用”是不同条件，二者都需要满足。

### 为启动段、稳定段和排空段分别列依赖

对 K 分块 Matmul，累加器贯穿 K 循环，ping/pong 在这里用于 A 的 L2 Buffer 输入槽。W 经 LDG/WL1 读取，准备下一块 W 的读取描述符不等于给 W 建立 L2 Buffer ping/pong。启动段先把 A 的第 0 块搬入 ping；稳定段在 PE 使用当前槽时准备下一块；最后一轮结束后，累加器才可以转换并写出。

下表表示三个 K 块的依赖安排，使用逻辑顺序而非固定周期。实际能否重叠由资源、输入就绪时间和编译后的同步决定。

| 阶段 | 当前计算 | 可以准备的输入 | 不允许的覆盖 |
|---|---|---|---|
| 启动 | 等待 A0 与 W0 就绪 | A0 装入 ping | 不能先计算第 0 块 |
| 第 0 轮 | A0/ping 与 LDG W0 | A1 装入 pong | 不能改写 ping |
| 第 1 轮 | A1/pong 与 LDG W1 | A2 装入 ping | 复用前须确认第 0 轮完成 |
| 第 2 轮 | A2/ping 与 LDG W2 | 无后续输入 | 不能提前写出最终 C |
| 排空 | 转换并写回累加器 | 按调度准备下一输出块 | C 写回期间保持源有效 |

Table: 三个 K 块的输入双缓冲依赖

只有一个 K 块时，没有下一轮可以预取；两个 K 块只有一次重叠机会；长 K 循环才可能形成稳定段。因此双缓冲测试至少覆盖 1、2、3 和多个 K 块，尤其保留奇数轮和 K 尾块。其资源代价必须在这些形状上都能接受，不能只展示长 K 的成功结果。

设每个 tile 的装载、计算和写回时间分别为 $L$、$C$、$S$，总共有 $n$ 个 tile。在三个阶段使用独立资源、没有额外冲突的理想模型中，顺序时间为 $n(L+C+S)$，充分流水后的时间近似为

$$
T_{\mathrm{pipe}}\approx L+C+S+
(n-1)\max(L,C,S).
$$

这是教学模型。实际搬入和写回可能共享通路，缓冲容量和同步也可能限制并发。少量 tile 的启动与排空占比较高，双缓冲带来的收益未必明显。用这条式子判断可能的收益空间，再用真实时间线验证是否出现稳定重叠。

### 有条件地启用双缓冲

编译器的双缓冲选项默认关闭，显式启用后才参与相应转换。它针对可识别的循环，不保证所有 kernel 都会改变。以下 ZECC 命令使用同一份 Matmul 源码，先生成基础策略的设备程序：

```bash
mkdir -p build/gemm-base build/gemm-double-buffer
gemm_flags="--num-vp=1 --num-dt=1"
ZEUS_COMPILER_EXTRA_FLAGS="$gemm_flags" \
zecc --compile-only-zbin \
  -c examples/matmul.py -o build/gemm-base/matmul.zbin \
  --kernel-name matmul_bf16 \
  --signature 'a_ptr=*bf16' --signature 'w_ptr_list=*i64' \
  --signature 'c_ptr=*bf16' \
  --signature M=i32 --signature K=i32 --signature N=i32 \
  --constant CORE_NUM=1 --constant BLOCK_M=128 \
  --constant BLOCK_K=128 --constant BLOCK_N=128
```

然后保持参数集合不变，仅增加双缓冲选项并使用另一个输出目录：

```bash
ZEUS_COMPILER_EXTRA_FLAGS="$gemm_flags --enable-double-buffer" \
zecc --compile-only-zbin \
  -c examples/matmul.py \
  -o build/gemm-double-buffer/matmul.zbin \
  --kernel-name matmul_bf16 \
  --signature 'a_ptr=*bf16' --signature 'w_ptr_list=*i64' \
  --signature 'c_ptr=*bf16' \
  --signature M=i32 --signature K=i32 --signature N=i32 \
  --constant CORE_NUM=1 --constant BLOCK_M=128 \
  --constant BLOCK_K=128 --constant BLOCK_N=128
```

这两条命令只编译，不执行算子。通过 Python JIT 比较时，在[Matmul 宿主封装](#matmul-example)的启动调用中分别设置 `zeus_compiler_extra_flags`，使用同一份 A、W 和 PyTorch 参考，并保留各自诊断目录。切换选项后重新确认实际特化，不能把不同配置的缓存产物混作同一次对照。

比较时首先确认候选实际形成了双缓冲，再检查正确性和各阶段重叠。双缓冲增加同时活跃的状态，可能使资源分配失败，或使其他优化机会变少。出现资源错误时，先检查 tile 和活跃缓冲的规模；出现输出错误时，保留原始失败用例，检查缓冲生命周期与同步，不能把删除同步当成性能优化。

双缓冲的三个常见无收益原因可以分别排查。第一，循环未被识别，生成代码与基线没有相关差异；第二，确实形成两个槽，但搬入和计算仍受同一资源或依赖串行限制；第三，原有流水已充分重叠，关键路径受读取带宽限制，而新增预取没有减少读取量或缩短等待。第三种提示继续增加预取深度的空间有限；前两种仍需要检查转换条件和资源映射。

## 执行单元并行与算子融合

### 区分两种 Executor 并行

Parallel-Executor 把多个相互独立的完整逻辑操作放到不同执行 lane。Multi-Executor 则把一个逻辑操作拆为多个 sibling。两者的工作粒度不同，应分别验证。一个 kernel 的不同操作可以使用不同机制，同一个逻辑操作的物理分配则必须保持唯一且一致。

Parallel-Executor 的关键前提是可证明的独立性。多个工作项必须有明确的输入输出范围，没有读后写、写后读或写后写冲突，且满足相应操作与资源约束。源码中两个数学表达式看起来相似，不足以证明它们可以并行；隐藏的指针别名、共享可写状态和顺序依赖都可能阻止分派。

在编译选项中启用 `--enable-parallel-executor`，并通过 `--parallel-executor-width` 设置候选宽度。Python JIT 可使用单次启动参数 `zeus_compiler_extra_flags` 传入这些选项。调参时不要同时改 kernel 数据流、tile 和并行开关。若为暴露独立工作先改写了源码，应保留三个版本。

| 版本 | 源码 | 并行分析 | 对照用途 |
|---|---|---|---|
| A | 原始实现 | 关闭 | 原始基线 |
| B | 改写后实现 | 关闭 | `B/A` 反映源码改写影响 |
| C | 与 B 相同 | 开启 | `C/B` 反映该开关的净影响 |

Table: 分离源码改写与并行配置的收益

检查生成 IR 和 trace 中实际采用的 lane，而不是仅检查命令行开关。报告各 lane 的工作量、重叠区间和空白区间。若新增 lane 后整体时间没有缩短，可能是工作量过小、读取带宽受限、等待同步，或关键路径已转移到其他单元；应沿完整执行区间定位。

### 让独立行或 head 出现在可分析的位置

适合 Parallel-Executor 的一个形态是“多个互不重叠的完整行分别归约并写回”。每个行块独立读取、拥有自己的临时量和输出，循环迭代之间没有累加状态。可把总行块循环作为候选，而不是把一个行内的平方和拆成多个有依赖的步骤。

Attention 中也应沿独立 head 分组。对于每个 head，序列块之间的 `m/l/o` 递推顺序必须保留；不同 head 可以有各自的递推状态。把代码改为“同一序列步上依次推进几个 head”，可能使相同的 VP 阶段更接近，但同时会增加活跃状态。每一组 head 的 Q、统计量、输出和 scratch 均应可证明不重叠。

一些看似独立的写入实际上会形成别名。例如迭代 i 写入 `out[i]`，同时读取 `out[i-1]`，存在跨迭代递推；两个指针来自同一块存储且偏移未知，也不能靠变量名不同证明独立。优先使用完整、规则的张量范围，让编译器有足够信息证明独立性。不能以“业务上不会撞地址”为由忽略接口未表达的条件。

本书把 Parallel-Executor 作为独立运算并行的首选试验方向。Multi-VP 改变单个逻辑操作的拆分方式，需要独立的正确性与收益验证；不要同时提高 Multi-VP 数量、Parallel 宽度和预取深度，再把一个总耗时变化归因于其中任意一项。

### 用数据流判断融合是否有价值

把两段源码放进同一个函数，不一定减少启动或中间结果写回。评估融合时应数清实际 kernel 启动次数、每个中间张量的外存读写、输出契约以及同时活跃的数据量。融合可能减少流量，也可能增加 L2 Buffer 压力，降低可利用的并行度。

[Fused Add RMSNorm](#fused-add-rmsnorm-example) 保留 residual 输出，并消除归一化阶段对 residual 的一次重新读取。只有归一化使用与独立算子链相同的 BF16 residual，才是数值契约相同的对照。若融合版本直接使用尚未转换的 FP32 和，比较的已是另一个计算过程。

还可以从“保留、重读、重算”三个选择评估中间值。RMSNorm 保留 X 可减少一次读取；两遍版本重读 X 换取更小的工作集。对于很便宜的索引或缩放常量，重新计算可能比存入临时张量再读回更合适；对于昂贵的矩阵乘结果，重算通常代价更高。应比较被删除的字节数与新增运算、活跃状态和同步，而不是默认所有融合都值得保留。

### 一条有先后顺序的调优路径

对尚未优化的 GEMM，可按以下顺序推进；每一步保留最近的正确版本，使用相同输入和计时边界比较基线与候选。

1. 用规则 A/W/C 描述符完成单核、多 K 块的正确计算，确认权重打包与输出坐标。
2. 计算主要工作集和尾块效率，选择少量 M/N/K tile 候选，排除容量明显不够或填充过大的组合。
3. 检查 A/W 的重复装载，按实际瓶颈尝试跨 N 复用 A 或跨 M 复用 W，观察新增累加器的资源代价。
4. 对合适的 K 循环尝试双缓冲，检查输入准备是否与 PE 计算重叠，以及换槽和排空是否正确。
5. 若 epilogue 或独立归约成为瓶颈，再考虑融合和 Parallel-Executor；保留数学定义、输出和精度。
6. 回到小 M、N 尾块、K 尾块与短循环，按有意义的 shape 区间选择配置。

向量与归约优先检查分工和搬运，Attention 优先检查页表与 LDG 访问。按代表形状计算基线时间与候选时间之比作为加速比；多形状汇总时注明权重，并保留回归项。
